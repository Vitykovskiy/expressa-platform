# Версионирование, выпуск и совместимость

Backend, front-office и back-office имеют независимые SemVer-версии в своих `package.json`. Версии до первого принятого MVP могут быть `0.x.y`; первый принятый MVP получает `1.0.0` для соответствующего компонента.

## Контракт выпуска

1. Оператор создаёт компонентный тег `backend-vX.Y.Z`, `front-office-vX.Y.Z` либо `back-office-vX.Y.Z` только на проверенном коммите `main`; это операционная предпосылка, а не проверка workflow.
2. Workflow проверяет формат компонентного тега, равенство версии `package.json` значению `X.Y.Z` и заголовок выпуска компонента в корневом `CHANGELOG.md`.
3. Workflow проверяет существование `sha-<полный SHA>` образа для текущего коммита, создаёт для его digest тег `vX.Y.Z` и сверяет итоговый digest. Образ не пересобирается.
4. Для staging создаётся `deploy/staging.env` с тремя canonical `@sha256` ссылками, записью в changelog и тегом `staging-vX.Y.Z`.
5. `staging-deploy.yml` разворачивает только этот набор digest-образов.

Workflow не доказывает успешность предшествующего CI или принадлежность тегируемого коммита `main`; эти проверки обязан выполнить оператор до тега. `latest` не является входом staging или будущей production-поставки. Совместимый набор может сочетать разные версии трёх компонентов; его источником истины служит staging-манифест.

## Совместимость

Backend добавляет совместимые изменения API до выпуска клиентов. Клиенты поддерживают `/api/v1`; несовместимое изменение требует нового базового пути API. Для development клиенты собираются с `VITE_API_BASE_URL=/`, поэтому используют backend той же среды через reverse proxy.

Теги образов, staging-манифест и staging-тег пока не созданы: выпуск не доказан. Production-процесс будет использовать тот же staging-digest без пересборки, когда среда будет добавлена отдельным решением.
