# ADR-013: организация features back-office

## Контекст

Рефакторинг back-office должен сделать код и структуру понятными разработчику,
который читает приложение с нуля. Технический DoD уже задаёт направление
`app -> pages -> widgets -> features -> entities -> shared`. При этом в
features/auth рядом находятся HTTP, состояние сценария и представление;
catalog, users и notifications смешивают логику сценария и UI. Названия соседних файлов помогают найти модуль,
но не показывают границу этих обязанностей.

[ADR-011](ADR-011-back-office-clean-slate.md) сохраняет технический стек,
слои и владельцев. Перестройка каталогов должна улучшить навигацию по коду,
сохраняя HTTP-контракты, состояние, команды и пользовательское поведение.

## Решение

Используем адаптацию Feature-Sliced Design в пределах действующего DoD:

- Сохраняем слои и существующие предметные области. Не добавляем пустые слои,
  каталоги для будущих задач или отдельную feature для каждого нажатия.
- В смешанных feature-каталогах разделяем `api` — HTTP, `model` — состояние
  и логику сценария, `ui` — компоненты, стили и presentation-модули. Сегмент
  появляется только при наличии соответствующего кода.
- Небольшие связные entity-каталоги сохраняем плоскими с предметными суффиксами
  модулей. Именованные типы и константы остаются рядом со своим владельцем
  в `*.types.ts` и `*.constants.ts`; общий склад деклараций не создаём.
- Композиция разных областей остаётся в `app` или потребляющей странице.
  Навигация конкретного маршрута принадлежит его `pages`-каталогу.
  Граница staff-экрана в `app` и layout в `widgets` уточнена в
  [ADR-014](ADR-014-back-office-composition-and-current-entry.md#экран-и-layout).
  Нижний слой не импортирует верхний. Существующие зависимости одного слоя
  проверяются владельцем затронутой области; перенос не добавляет новую
  бизнес-зависимость между соседними областями.
- Сохраняем явные именованные импорты модулей и относительные пути внутри
  области. Не вводим обязательные `index.ts`, глобальные barrels, alias rewrite
  или файлы-прокси ради переноса.

Это локальная адаптация. FSD требует публичный API срезов и сегментов App/Shared,
который скрывает внутреннюю структуру от внешних потребителей; здесь сохраняются
прямые пути модулей. Основание и границы подхода: официальные
[слои](https://feature-sliced.design/docs/reference/layers),
[срезы и сегменты](https://feature-sliced.design/docs/reference/slices-segments),
[публичный API](https://feature-sliced.design/docs/reference/public-api).

## Переход

Решение задаёт целевую организацию; оно не означает, что исходники уже перенесены.
Текущая структура и целевые правила различаются в
[локальной карте](../../../back-office/docs/80-conventions/code-layout.md).
Каждая ограниченная предметная партия владеет своим переносом, соседними
декларациями и необходимыми заменами путей у потребителей. Такие замены
не меняют логику потребителя. После переноса не остаются совместимые заглушки,
двойные импорты и устаревшие ссылки документации.

Публичные URL текущего `/service-worker.js`, manifest и assets сохраняются.
Прежнее общее условие сохранения worker URL заменено в части `/sw.js`
[ADR-014](ADR-014-back-office-composition-and-current-entry.md#текущий-вход-и-снятые-переходы):
его переход снимается вместе с прежними `/queue`, `/availability` и `/menu`.
Это целевой контракт, а не утверждение о выполненном удалении. Перенос исходников
не меняет порядок CSS, DOM, сетевые исходы, роли, владение состоянием,
его срок жизни или семантику конкурентных команд. Новое поведение требует
отдельного основания в предметном контракте. Автоматизированные тесты
до явной приёмки пользователем запрещены; после неё нужны прямые указания
пользователя. Применимые существующие нетестовые проверки и независимое review
остаются обязательными по DoD.

## Последствия

Читатель получает предсказуемое место для HTTP, логики сценария и представления.
Сохраняются Vue 3, Vuetify, TypeScript, Vite, Pinia и автономность клиента.
Переименование каталогов само по себе не завершает рефакторинг: каждая область
требует содержательной переработки и независимой проверки читаемости.

Прямые импорты оставляют связь потребителей с путями: при переносе необходимо
обновлять их согласованно. Обязательный barrel для каждого среза добавил бы
переходы без установленной пользы текущим потребителям. Новая общая библиотека,
смена framework или владельцев состояния не обоснованы этой задачей.
Если модулю понадобится реальная граница инкапсуляции, её контракт рассматривается
отдельно по действующим правилам ответственности и текущим потребителям.
