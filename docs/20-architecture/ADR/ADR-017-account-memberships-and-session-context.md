# ADR-017: аккаунт, участия и контекст сессии

## Контекст и полномочия

Пользователь требует отдельные вкладки сотрудников и зарегистрированных клиентов,
без категории «Без роли», и использование одного телефона в обоих приложениях.
Сотрудник имеет роль «Бариста» либо «Администратор», клиент не имеет staff-роли.
Принятая очистка макета разрешает реализацию. Техническое решение A02/2 прошло
независимую приёмку R02/2; этот ADR переносит его в долговременный контракт.
Статус accepted относится к решению, а не к готовности кода, API или runtime.

Текущая схема хранит исключительную `users.role`; она не выражает независимые
участия. Два аккаунта на один телефон разделили бы вход и историю заказов.

## Решение

Сохраняем один `users.id` на нормализованный телефон. Отдельные `customers` и
`employees` задают независимые участия; отсутствие одного не запрещает другое.
Имя одно, принадлежит аккаунту. Различие существующего имени и имени первой
регистрации/добавления сотрудника даёт явный конфликт, без перезаписи.
Окончание работы отключает рабочий доступ, сохраняя staff-роль, клиента и историю.
Глобальная блокировка аккаунта остаётся отдельной операцией.

Сессия и push-привязка получают неизменяемый проверенный `customer|staff`
контекст. Права определяются текущими данными БД и контекстом, не scalar `role`
в ответе или объединением участий. У customer-контекста push v2 сохраняется
до завершения регистрации; список клиентов и заказы требуют customer-участия.

Auth v2 расширяется добавочно. Новые административные ресурсы employees и
customers находятся в v3. Опубликованные account-команды users сохраняются
с точными проекциями и переводом команд в ту же модель участий; отдельного
хранилища роли или второго механизма авторизации нет. Их удаление не разрешено.
В `/users` остаются две вкладки, а не новые разделы навигации.

## Граница замещения

В [ADR-012](ADR-012-back-office-source-contract.md) заменены только предположения
об исключительной роли аккаунта, смешанном списке пользователей как UI,
замене роли customer/staff и отзыве обоих контекстов при рабочем изменении.
Published users API сохраняется по новой семантике. Серверная авторизация,
проверенный actor/requestId, аудит, атомарность, self/last-admin защита,
запрет неявного повтора и остальные контракты каталога, заказов, настроек и
навигации сохраняются. [ADR-009](ADR-009-explicit-logout-push-contract.md)
сохраняет capability-only logout fallback; активная ветка учитывает контекст.

## Последствия и границы

Изменения auth, хранения, staff и push реализуются согласованно до приёмки
клиентов. Данные local/test/development пересоздаются; миграций и backfill нет.
Сохранение клиентской истории при отключении работы — runtime-инвариант,
не обещание сохранения одноразовой БД между поставками.

Не вводятся HR-статусы, разные рабочие/личные имена, несколько организаций,
новый customer administration UI или независимые сессии на общем API host.
Пересмотр нужен при отдельном требовании таких возможностей, постоянных данных
либо удаления опубликованного API. Внедрение, OpenAPI/snapshot-публикация,
ручная runtime/визуальная проверка и пользовательская приёмка остаются отдельными
результатами. Тесты и Git/deploy-действия этим решением не разрешаются.
