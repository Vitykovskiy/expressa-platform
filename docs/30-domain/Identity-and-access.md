# Идентификация и доступ

Ниже — целевой контракт [ADR-017](../20-architecture/ADR/ADR-017-account-memberships-and-session-context.md).
Текущая схема хранит независимые участия и фиксированный контекст, без
исключительной `users.role`. Этот нормативный документ сам по себе не
подтверждает код, публикацию API, runtime или независимую приёмку.
Транспорт принадлежит
[Authentication API](../50-interfaces/Authentication-API.md), поля хранения —
[данным backend](../../backend/docs/40-data/PostgreSQL-and-migrations.md).

## Аккаунт и участия

Нормализованный телефон E.164 определяет единственный аккаунт со стабильным
`users.id`. Customer- и employee-участия независимы, каждое существует не более
одного раза на аккаунт. OTP без регистрации создаёт только аккаунт.
Наличие employee или имени не означает customer-регистрацию. Зарегистрированный
клиент попадает в «Клиенты» и может оформлять/читать/повторять только свои заказы.
У него нет staff-роли. Сотрудник имеет обязательную `barista|administrator`,
включая период отключённого рабочего доступа. Один человек может быть в обеих
вкладках с тем же ID/телефоном и пользоваться обоими приложениями.

Имя — одно nullable-поле аккаунта, не два имени участий. `null` допустим для
OTP/CLI/bootstrap, подставное имя не создаётся. Регистрация требует настоящее
непустое имя. При первом customer-участии отсутствующее имя заполняется;
существующее отличающееся имя даёт `USER_NAME_CONFLICT`. При уже завершённой
регистрации повтор возвращает сохранённый профиль без перезаписи. Параллельные
регистрации сходятся к первому завершению. Добавление employee также заполняет
только отсутствующее имя и явно отклоняет конфликт. Customer-участие, account ID,
заказы, снимки, события и idempotency keys не переназначаются рабочими командами.

## OTP и ограничения выдачи

OTP нормализует российский телефон в E.164, принимает шесть цифр, действует
пять минут и допускает пять попыток. На номер один открытый challenge во всей
системе, без отдельных SMS-каналов приложений. Повторный запрос, в том числе
из другого клиента/reload, получает `429 AUTH_RATE_LIMITED` до истечения
cooldown с остатком в `Retry-After`. Параллельная выдача сериализуется.

Успешная проверка потребляет challenge; разрешённый resend потребляет
предыдущий. После успеха или пяти неверных попыток новый request доступен сразу.
Отдельный security throttle учитывает номер, проверенный адрес источника и
общий SMS-бюджет в часовом окне. Отказ по UX cooldown бюджет не расходует;
исчерпание возвращает остаток окна. Глобально заблокированный аккаунт получает
обычный отказ проверки OTP, без раскрытия наличия или статуса аккаунта.

## Контекст и политики

Контекст сессии `customer|staff` задаётся при создании и не меняется при refresh,
смене роли или участия. Обе новые версии клиентов явно запрашивают свой контекст;
точное поведение при отсутствии поля определено в HTTP-контракте. Staff-контекст
без включённого employee может аутентифицировать аккаунт для `/me` и экрана
отказа, но не имеет staff/customer бизнес-прав.

Access JWT сохраняет `aud/iss/sub/sid/iat/exp`, где `sub=users.id`,
`sid=sessions.id`; доверенной роли или выбираемых клиентом capabilities нет.
SessionGuard проверяет соответствие subject/session, срок, отзыв, глобальную
блокировку и читает актуальные участия/рабочий доступ из БД. Контекст не
перевычисляется. Обязательные политики после этой проверки:

| Политика               | Условие                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| Customer               | customer-контекст и завершённое customer-участие                                              |
| Staff                  | staff-контекст и включённое employee-участие                                                  |
| Administrator          | Staff с ролью administrator                                                                   |
| CustomerOrBarista      | аутентифицированный customer-контекст, в том числе до регистрации, либо Staff с ролью barista |
| Регистрация            | customer-контекст; предварительное customer-участие не требуется                              |
| `/me`, refresh, logout | аутентифицированная сессия, без требования staff-участия; logout fallback описан отдельно     |

Scalar `role` опубликованного v2 DTO — только совместимая транспортная проекция,
не участие, разрешение или сохранённое поле аккаунта. Клиенты используют контекст
и участия. Staff-токен не получает customer-заказы/регистрацию, customer-токен
не получает staff API даже у одного человека. Потеря administrator очищает
admin-owned клиентское состояние, даже если staff-сеанс ещё действителен.

Access token хранится в памяти, refresh — host-only HttpOnly Strict cookie.
Независимые восстанавливаемые customer/staff-сессии поддерживаются только на
разных same-origin app hosts с собственными `/api/v2` и `/api/v3` proxy.
Разные порты одного host не изолируют cookie; общий API host/один host не
обещает независимых сессий. Cookie name/path/Secure и сроки остаются прежними.
Refresh ротирует credential, сохраняет контекст и не оживляет отозванную сессию.

## Рабочий доступ и глобальная блокировка

Enrollment находит либо создаёт аккаунт по уникальному телефону и присоединяет
employee в одной административной транзакции. Customer-участие и история
сохраняются; новый employee сам по себе customer не создаёт. Существующий
employee, включая отключённый, даёт phone conflict: используется access-команда.
Глобальная блокировка запрещает enrollment и восстановление рабочего доступа
до явной глобальной разблокировки. Точные ошибки — в HTTP-контракте.

Смена staff-роли сохраняет рабочий доступ и клиента. Окончание работы —
`enabled=false`: employee, его роль, аудит и клиентская история остаются.
Повторное включение не восстанавливает сессии или подписки. Реальная смена роли
и оба перехода рабочего доступа атомарно отзывают все STAFF-сессии и удаляют
только STAFF push-привязки цели. Это включает остаточное состояние отключённого
employee и denied STAFF-сессии при повторном включении. Enrollment отзывает
прежние denied STAFF-сессии, чтобы токен не получил новые права молча.
Customer-сеансы/привязки и участие при этих действиях сохраняются.

Глобальный account block остаётся отдельной опубликованной users-командой:
отзывает ВСЕ контексты сессий и удаляет ВСЕ push-привязки цели. Глобальный
unblock возвращает лишь право нового входа. Рабочая кнопка «Блокировать» не
вызывает эту команду; `accountBlocked` отличает глобальный запрет от work disable.
No-op не пишет новый аудит и не повторяет отзыв; итог определяется сохранёнными
участиями/доступом, а не совпадением scalar role.

Каждая HTTP-команда проверяет активного administrator и действующую actor-сессию
повторно внутри транзакции. Запрещены self-disable, self-global-block,
self-demotion и лишение последнего глобально незаблокированного включённого
administrator. Подсчёт использует employee role/access JOIN users, не проекцию
`role`. Actor и subject — стабильные account IDs; requestId проверен сервером.
Нет client-supplied actor, удаления участия или отдельного HR lifecycle.

## Транзакции и блокировки

Изменения состава администраторов сериализуются существующей advisory lock
`expressa:staff-users:membership`. Для staff/global-access/push порядок таков:
сначала membership advisory lock, затем участвующие users по ID, строки участий,
сессии, push-привязки. OTP, регистрация и refresh берут account перед
membership/session и никогда не берут advisory lock после account lock.
Под блокировками повторно проверяются account, полномочия и session ownership,
context/activity. Бизнес-запись, аудит и отзыв фиксируются либо откатываются
вместе. SMS/push-внешние эффекты не выполняются внутри незавершённой транзакции.

## Push и logout

Контекст привязки выводится из проверенной сессии, не принимается как grant
из запроса. В существующей push-транзакции заново проверяются account/session
и текущее employee-участие. Customer-контекст для v2 inspect/association/delete
требует действующую незаблокированную сессию, НЕ завершённую регистрацию.
Успех push не регистрирует клиента, не добавляет его в «Клиенты» и не разрешает
заказы. Staff-контекст требует включённого barista; administrator не становится
получателем новых заказов. Через customer-контекст administrator может получать
собственные customer-уведомления.

`findForUser` выбирает только customer-привязки аккаунта без global block и без
требования регистрации. `findForStaff` — только staff-привязки включённых barista
незаблокированных аккаунтов. Контекст входит в hydration/snapshot. Цель
уведомления не выводится из другого участия владельца.

Endpoint глобально уникален: одна привязка/контекст одновременно. Enable
идемпотентен только при совпадении аккаунта, контекста и proof. Customer transfer
возможен только из customer-привязки действующему customer-context actor,
с точным proof и expectedVersion, независимо от регистрации. Staff не переносит
чужую привязку. Cross-context transfer, даже для того же аккаунта, даёт
`PUSH_ASSOCIATION_CONFLICT`; смена возможна через явные delete/enable с нужным
контекстом. Inspect current/other сравнивает account И context. Сохраняются
privacy, CAS, proof и защита от удаления по устаревшему snapshot.

Активный logout удаляет только точное совпадение user+context+endpoint+keys
и отзывает эту сессию. Missing/invalid refresh credential сохраняет
[ADR-009](../20-architecture/ADR/ADR-009-explicit-logout-push-contract.md)
capability-only exact-proof deletion без отзыва неизвестных сессий. Cookie,
storage-failure, browser permission и локальная подписка сохраняют прежнюю
семантику [HTTP logout](../50-interfaces/Authentication-API.md#current-customer-logout).
