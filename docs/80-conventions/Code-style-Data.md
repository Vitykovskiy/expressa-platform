# Внешние данные и ошибки

Применяется к новому и изменяемому авторскому коду по [общему стандарту](Clean-code.md). Приёмка — [общий DoD](Definition-of-Done.md).

## Граница доверия и обработка

Внешние данные принимаются как недоверенные и проверяются один раз при
переходе в типизированный контракт. Для необработанного значения используется
`unknown`; assertion не является runtime-проверкой. После проверки внутренний
код доверяет контракту до новой границы. DTO описывает обмен, не содержит
бизнес-команд и не передаётся напрямую в UI вместо модели владельца.
Маппинг чистый; отдельная модель представления нужна при отличии отображения.

Неизвестный контракт отмечается как неизвестный. Endpoint, поле или
альтернативный формат не угадываются. Внешний SDK изолируется у адаптера,
когда иначе его детали проникают в предметный слой; обычный framework-тип
не получает wrapper без причины. Выбор структур данных или поведения
учитывает текущую ось расширения и инварианты, без обязательных rich-классов.

Сбой не превращается в успешный пустой список, запасное поле или выдуманное
значение. Предусмотренные отсутствие, default и альтернативный формат
сохраняются. Ошибки различаются по реакции потребителя; универсального
требования «только исключения» нет. Обработка имеет владельца, сохраняет
причину и разрешённый безопасный контекст, не копируется по вызовам.
Ресурсы освобождаются при завершении, ошибке и отмене; частичный успех
не объявляется полным. Новая диагностика, сообщение или восстановление
из этого стандарта не выводятся.

В backend действуют [контракты ошибок и транзакций](Code-Definition-of-Done-backend.md#контракты-ошибки-и-побочные-эффекты).
В клиентах API-слой не владеет UI-состоянием и не зависит от компонентов,
Pinia, DOM или маршрута. Конкретное отображение ошибок, восстановление,
доступность и общие параметры UI остаются у существующих контрактов
[front-office](../../front-office/docs/30-conventions/UI-contracts.md) и
[back-office](../50-interfaces/Back-office-UI.md).
Barsim toast, resolver и диагностика не становятся инфраструктурой Expressa.

## Пример проверки и маппинга

**Пример E13, C5/C4.** Иллюстративный внешний объект имеет непустой `id` и обязательное `title`, допускающее непустую строку либо `null`. Домен использует имя `name`. Это учебный контракт, не описание API приложения. Виртуальный `catalog-item.types.ts`:

```typescript
export interface CatalogItem {
  readonly id: string;
  readonly name: string | null;
}
```

Антипример `catalog-item.mapper.ts` доверяет assertion и выдумывает название при отсутствии:

```typescript
import type { CatalogItem } from "./catalog-item.types";

export function mapCatalogItem(value: unknown): CatalogItem {
  const dto = value as { id: string; title?: string };
  return { id: dto.id, name: dto.title ?? "Без названия" };
}
```

Исправление в том же файле:

```typescript
import type { CatalogItem } from "./catalog-item.types";

export function mapCatalogItem(value: unknown): CatalogItem {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new Error("Ожидался объект каталога");
  }

  if (
    !("id" in value) ||
    typeof value.id !== "string" ||
    value.id.trim().length === 0
  ) {
    throw new Error("Некорректный ID каталога");
  }

  if (!("title" in value)) {
    throw new Error("Нет поля title");
  }

  const title = value.title;

  if (title === null) {
    return { id: value.id, name: null };
  }

  if (typeof title !== "string" || title.trim().length === 0) {
    throw new Error("Некорректное название каталога");
  }

  return { id: value.id, name: title };
}
```

Порядок виден: объект → ID → наличие поля → разрешённое отсутствие → строка. Пропущенное поле, неверный тип и пустая строка ошибочны; `null` сохранён. ID и название не нормализуются скрыто: `trim()` здесь проверяет пустоту, возвращается исходная строка. Нет casts, HTTP и восстановления пустым массивом. Оператор `in` задаёт доступный контракт свойств; если конкретный API требует только собственные свойства, это дополнительный инвариант его границы.

## Выбор представления и границы

При устойчивом наборе видов данных и новых операциях подходят явные структуры и чистые функции; новый вид может потребовать изменения разбирающих функций. При текущем расширении семейства вариантов с устойчивыми операциями поведенческий контракт защищает потребителей, но новая операция может потребовать изменения реализаций. Выбор учитывает реальную ось изменения и инварианты по [SOLID-O](Code-style-Contracts.md); rich-класс или registry для будущего не требуются.

## Наблюдение при приёмке

Проследите недоверенное значение до проверки, предметной модели и реакции на ошибку. Пропуск обязательного поля, допустимый `null` и сетевой отказ должны иметь предусмотренные разные результаты. Сравните формат транспорта и потребителя; в API-слое нет UI-state. Подстановка вместо сбоя и потеря причины ошибки блокируют приёмку.
