# Формы и валидация

Применяется к новому и изменяемому авторскому коду по [общему стандарту](Clean-code.md). Приёмка — [общий DoD](Definition-of-Done.md).

## Значения, сброс и проверка

Форма имеет типизированные значения и определённую семантику начального
состояния, `null`, пустой строки и сброса. Синхронный валидатор чистый;
поддерживаемая асинхронная проверка делегирует запрос API-владельцу и различает
pending, невалидное значение и недоступность проверки. Ошибка схемы не
становится успешной валидацией. Это не вводит Formly, Reactive Forms или
новую библиотеку форм; сохранение и обратная связь следуют контракту клиента.

## Наблюдение при приёмке

Сравните начальное значение, пользовательское редактирование и сброс с контрактом. Различайте чистую производную и редактируемый черновик по [владению состоянием](Code-style-State.md). При сохранении проверяются payload, допустимость повторной команды, завершение и обратная связь существующего сценария; документ не назначает новую политику или библиотеку.

## Пример сброса nullable-значения

**Учебная иллюстрация, не форма продукта.** Действующий контракт разрешает `string | null`, начальное состояние — `null`, сброс должен восстановить отсутствие. Антипример инициализирует поле пустой строкой и при сбросе снова присваивает `""`: отсутствие становится другим значением.

Исправление сохраняет тип и начальный `null`, редактирование задаёт строку, команда сброса возвращает `null`. Потребитель обрабатывает разрешённое отсутствие отдельно; обязательное непустое название потребовало бы другого подтверждённого контракта. Это не выбор библиотеки или правила нормализации пустой строки для Expressa.

Для асинхронной проверки различайте: выполняется проверка, значение невалидно, проверка недоступна. Недоступность не даёт ни успешной валидации, ни выдуманного предметного отказа. Сохранение и повтор следуют [политике сценария](Code-style-Async.md), полевая обратная связь — UI-контракту своего клиента.
