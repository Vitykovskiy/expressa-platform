# Definition of Done для front-office

> **КРИТИЧНО: приоритет содержательного результата.** Критерии применяются
> для устранения доказанной проблемы или реализации необходимого изменения в
> production-коде `front-office`. Правка остаётся, только если она упрощает
> ответственность, зависимости, контракт, навигацию или сопровождение. Если
> текущий код уже понятен и однозначен, изменение только формы, имени или
> расположения без проверяемой пользы не выполняется.

Этот документ задаёт критерии приёмки целевого production-кода автономного
клиента `front-office`. Он применяется к Vue 3, Vuetify, TypeScript, Vite и
Pinia после появления реализации. Архитектурная структура и автономность
клиента определены в [[../20-architecture/Client-architecture|Архитектуре
клиентов]] и [[../20-architecture/Repository-boundaries|Границах приложений]].

## Простота и ответственность

- В production-коде нет неиспользуемых параметров, полей, веток, функций,
  файлов, совместимых оболочек и заготовок для возможного будущего сценария.
- Общий код появляется только для нескольких существующих мест использования
  и остаётся проще отдельных реализаций.
- Функция имеет предметное имя, понятные входы и одну связную ответственность.
  Основной сценарий читается линейно; самостоятельный предметный шаг,
  инвариант или несколько связанных эффектов выносятся в именованную функцию,
  когда это делает сценарий понятнее.
- Тернарный оператор выбирает значение. Ветвление сценария выражается явной
  веткой или именованной функцией.
- Сложная конструкция получает краткий комментарий о назначении и существенном
  инварианте; комментарий не пересказывает строки кода.

## Типы и внешние данные

- TypeScript описывает границы и предметные данные. `any`, приведения типов
  без проверки и неявные nullable-контракты не скрывают неопределённость.
- Данные из HTTP, браузерного хранилища, URL и иных внешних источников
  принимаются как недоверенные и проверяются при переходе в типизированный
  контракт приложения.
- DTO принадлежат API-границе. После проверки они преобразуются в модель,
  удобную владельцу сценария; DTO не передаются напрямую в UI и хранилища
  предметного состояния.
- Нарушение внешнего контракта завершает сценарий явной ошибкой. Код не
  подставляет другое поле, формат, поведение или значение по умолчанию вместо
  ожидаемых данных. Разрешённое отсутствие значения выражается отдельным
  состоянием и обрабатывается явной веткой.

## Направление слоёв

- Если в front-office применяется рекомендуемая в архитектуре структура
  `app/pages/widgets/features/entities/shared`, `app` собирает приложение и
  его инфраструктуру; `pages` владеют составом страницы; `widgets` объединяют
  несколько областей страницы; `features` реализуют прикладное действие;
  `entities` содержат предметную модель и её операции; `shared` содержит
  переиспользуемые внутри front-office примитивы `api`, `ui`, `lib` и `config`.
- При использовании этой структуры зависимости направлены от `app` и `pages`
  к нижележащим слоям:
  `pages -> widgets -> features -> entities -> shared`. Нижний слой не
  импортирует верхний и не знает о его состоянии или UI-композиции.
- В такой структуре `shared` остаётся локальным для `front-office`: в нём нет
  типов, DTO, компонентов, конфигурации или импортов из `back-office`. Общий
  для двух клиентов код не создаётся в обход их автономных границ.

## Vue-компоненты и composables

- Компонент отвечает за представление и локальное взаимодействие. Он получает
  данные и команды через типизированные `props` и `emits`, не дублирует
  предметную логику и не скрывает её в шаблоне.
- Компонент, composable и Pinia store имеют предметное имя и одну основную
  роль. Composable выделяется для повторно используемой реактивной или
  прикладной логики, а не как оболочка одного очевидного выражения.
- Локальное UI-состояние остаётся у ближайшего владельца. Состояние, нужное
  нескольким независимым частям одного сценария, принадлежит его Pinia store;
  глобальным store не передаётся состояние страницы или одноразового виджета.
- Pinia store публикует минимальный типизированный контракт состояния,
  вычислений и команд. Он не становится неявным контейнером маршрута, DOM,
  экземпляров компонентов или несвязанных сценариев.

## Реактивность и побочные эффекты

- Производное состояние выражается вычислением из источника, а не копированием
  между реактивными значениями. Изменения выполняются через владельца
  состояния без прямой мутации полученных данных.
- `watch` и `watchEffect` используются для внешнего побочного эффекта, который
  нельзя выразить вычислением или явной командой. Зависимости, отмена и
  очистка эффекта определены там, где он создаётся.
- Загрузка, сохранение, навигация, работа с браузерным API и уведомления
  запускаются явной командой владельца сценария. Конкурентный запуск одной
  операции имеет понятную семантику: отмена, игнорирование, очередь или
  независимое выполнение.
- Ошибка, загрузка и отсутствие данных представлены явными состояниями
  владельца сценария. Отменённая или устаревшая операция не выдаётся за ошибку
  пользователю.

## API и интерфейс

- API-клиент выполняет запрос, проверяет ответ и преобразует DTO; он не владеет
  UI-состоянием, DOM, маршрутом или актуальностью пользовательского выбора.
- Vuetify-компоненты используются для представления и взаимодействия. Обёртка
  над компонентом создаётся только при повторяемом контракте front-office, а
  не для механического проксирования его свойств.
- Шаблон не содержит сложных преобразований, запросов, записи в store или
  неявных побочных эффектов. Он отображает подготовленное состояние и вызывает
  именованные команды.

## Тестируемость и приёмка

- Границы API, преобразование DTO, предметные вычисления, команды store и
  composables изолируемы от сети, времени, браузерного хранилища и UI.
- Исправление дефекта включает регрессионный тест, воспроизводящий его причину
  или наблюдаемое неверное поведение до исправления.
- Production diff не содержит несвязанных изменений, временного кода, `TODO`,
  отладочного вывода и отключённых проверок.
- Изменённое использование API Vue, Vuetify, Pinia, Vite, TypeScript или иной
  библиотеки сверяется с документацией через Context7 по точной версии из
  manifest или lock-файла; при отсутствии такого источника используется
  официальная документация.
- Приёмка запускает только инструменты, настроенные в `front-office` для
  затронутого production-кода: проверки типов, форматирования, линтера,
  сборки и тестов, если они объявлены конфигурацией приложения. Команды,
  сценарии и результаты не выдумываются при отсутствии настройки.
