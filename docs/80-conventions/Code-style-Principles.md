# Принципы выбора решения

Применяется к новому и изменяемому авторскому коду по [общему стандарту](Clean-code.md). Приёмка — [общий DoD](Definition-of-Done.md).

Все примеры ниже учебные; их виртуальные файлы и контракты заданы в тексте, это не API или файлы Expressa.

## KISS и DRY

### KISS

Выбирайте наименее сложное решение текущего достижимого сценария. У каждой
ветки, функции, прослойки, параметра и настройки есть действующий потребитель
или необходимая роль в сценарии. Прокси без ответственности, фиктивные режимы,
каркасы для будущего расширения и извлечения только ради сокращения строк
не добавляются.

Сложность оценивается по пониманию и сопровождению. Лимитов строк, аргументов
или методов этот стандарт не вводит. Оптимизация опирается на подтверждённую
проблему, ограничение и доступные измерения; предполагаемый выигрыш не
оправдывает скрытые зависимости. Это правило не разрешает создавать новый
benchmark или измеритель.

### DRY

Одно изменяемое предметное правило имеет одного владельца. Перед объединением
проверьте одинаковый смысл, причину изменения и существующих потребителей.
Общая реализация должна упрощать их код и сохранять границы приложений и слоёв.
Одинаковый синтаксис разных правил не требует объединения; несвязанные действия
не объединяются флагами и расширением публичного API.

Одинаковые UI-обязанности используют существующего локального владельца по
[Vue style](../40-quality/Vue-code-style.md) и UI-контракту своего клиента.
Различия имеют предметное объяснение. Общий код между автономными клиентами
не создаётся в обход [границ приложений](../20-architecture/Client-architecture.md#границы-совместимости).
Предписанный архитектурой порт или адаптер сохраняется и при одном потребителе:
его ответственность — защита действующей границы.

## Примеры выбора решения

**Пример E01.** Иллюстративный модуль формирует название из уже проверенной непустой строки. Требуется только удалить крайние пробелы; режимов преобразования нет. Антипример `title.mapper.ts` добавляет недостижимый выбор:

```typescript
export function normalizeTitle(title: string): string {
  const trimEnabled = true;
  const transform = (value: string) => value.trim();
  return trimEnabled ? transform(title) : title;
}
```

Исправление в том же виртуальном файле:

```typescript
export function normalizeTitle(title: string): string {
  return title.trim();
}
```

Вход, результат и отсутствие эффектов сохранены. Удалён фиктивный режим и прокси; проверка внешнего значения остаётся у границы данных. Если появятся реальные различные правила, их контракт рассматривается заново.

**Пример E02.** Условный редактор имеет две текущие команды: добавление строки и импорт. Обе применяют одно правило владельца: количество — положительное целое число. В `quantity-policy.ts` нельзя поддерживать две копии:

```typescript
export function canAppendQuantity(value: number): boolean {
  return Number.isInteger(value) && value > 0;
}

export function canImportQuantity(value: number): boolean {
  return Number.isInteger(value) && value > 0;
}
```

Исправление — одна предметная проверка в `quantity-policy.ts`, импортируемая обоими потребителями:

```typescript
export function isValidQuantity(value: number): boolean {
  return Number.isInteger(value) && value > 0;
}
```

Оба потребителя принимают и отклоняют те же числа. При изменении единого правила корректируется один владелец. Очевидный `0` здесь означает границу положительного числа, а не скрытый режим. Проверка количества страниц другого сценария может выглядеть так же, но иметь другого владельца и будущую причину изменения: объединять её только по синтаксису нельзя.

## Наблюдение при приёмке

Назовите достижимого потребителя каждой конструкции и одну причину изменения объединяемого знания. Отсутствующий потребитель или объединение разных правил без пользы блокируют приёмку. Предписанный порт сохраняет архитектурную ответственность и при одном потребителе.
