# Definition of Done для production-кода back-office

> **КРИТИЧНО: Приоритет содержательного результата.** Критерии DoD применяются, когда изменение приносит проверяемую пользу: уточняет ответственность, контракт, зависимость, поведение или сопровождаемость. Формальная правка формы, имени или расположения без такой пользы не требуется.

Документ определяет готовность production-кода автономного PWA `back-office` на Vue 3, Vuetify, TypeScript, Vite и Pinia. Он применяется к новой реализации, изменению и приёмке кода приложения; требования к продуктовым сценариям, поставке и инфраструктуре находятся вне этой ноты. Границы приложения и рекомендуемая структура определены в [[../20-architecture/Client-architecture|Архитектуре клиентов]] и [[../20-architecture/Repository-boundaries|Границах приложений]].
Для всего UI-кода обязательны [[../40-quality/Definition-of-done|UI DoD]],
[[../40-quality/Vue-code-style|стиль Vue-кода]],
[[../40-quality/UI-accessibility|доступность]] и
[[../40-quality/Validation-strategy|стратегия проверки]].

## Простота и ответственность

- Код добавляется для текущего достижимого сценария. Неиспользуемые параметры, поля, ветки, функции, файлы и оболочки не остаются в production-коде.
- Общая абстракция допустима для нескольких существующих потребителей, когда она проще отдельных реализаций. Одноразовая форма не получает отдельный тип или helper, если вывод TypeScript сохраняет понятный контракт.
- Функция имеет предметное имя, понятные входы и одну связную ответственность. Основной сценарий читается линейно; самостоятельный шаг выносится только когда это проясняет назначение, инвариант или тестирование.
- Комментарий объясняет неочевидное решение или существенный инвариант, а не пересказывает код.

## Типы и внешние данные

- `any` не используется. Внешние данные считаются недоверенными до проверки их формы и обязательных значений на границе приложения.
- DTO описывает контракт обмена с API и не подменяет модель, которую используют компоненты и состояние. Преобразование DTO в модель является явной, чистой операцией без UI, состояния и сетевых побочных эффектов.
- Каждый файл имеет одну зону ответственности. Все именованные `type`, `interface`, `enum` и другие контракты располагаются в соседнем `*.types.ts`; все константы уровня модуля, предметной области и конфигурации — в соседнем `*.constants.ts`. Файл реализации содержит только исполняемое поведение и не смешивается с объявлениями типов и констант. Локальные выводимые типы и значения внутри функции допустимы, если принадлежат только её алгоритму. Тест может хранить данные, типы и константы, используемые только этим spec; общие тестовые контракты и данные выносятся отдельно.
- Отсутствующее значение допускается только как явное состояние модели и обрабатывается отдельной веткой. Код не подставляет другое поле, формат, текст или значение по умолчанию для продолжения работы с недостоверными данными.
- Ошибка контракта и ошибка запроса имеют явное, безопасное для UI состояние. Альтернативная форма данных допустима только как явно определённая часть контракта.

## Слои и зависимости

Исходный код следует направлению `app -> pages -> widgets -> features -> entities -> shared`: верхний слой собирает нижние, а нижний не импортирует верхний. `app` владеет инициализацией приложения, `pages` -- композицией маршрута, `widgets` -- самостоятельным блоком страницы, `features` -- действием пользователя, `entities` -- предметной моделью, `shared` -- только локальными техническими и UI-примитивами.

- Код размещается в самом узком слое, который владеет его ответственностью. Перенос в `shared` обоснован несколькими существующими потребителями внутри `back-office`.
- `shared` не зависит от предметных DTO, моделей и пользовательских областей. `features`, `entities`, `widgets`, `pages` и `app` не образуют обратных импортов.
- `back-office` автономен: запрещены импорты исходного кода, типов, компонентов, конфигурации и тестовых артефактов из `front-office`.

## Компоненты, composables и Pinia

- Компонент отвечает за представление и пользовательские события. Он получает явные `props`, сообщает действия через `emits` и не скрывает загрузку данных или владение состоянием в представлении.
- Компонент-контейнер собирает страницу или блок; отображающий компонент не обращается к API и не меняет состояние другой пользовательской области.
- Composable выделяется для повторно используемого связного поведения. Его возвращаемый контракт минимален и понятен; одноразовая локальная реактивная логика остаётся рядом с владельцем.
- Store Pinia владеет состоянием и прикладными командами своей области. Store не становится прокси для API: сетевой контракт остаётся в локальном API-слое, а преобразование DTO не смешивается с изменением состояния.
- Состояние меняется только через владельца: публичный контракт не раскрывает изменяемые внутренние ссылки, если потребителю достаточно чтения или команды.

## Реактивность и побочные эффекты

- Производные значения выражаются через `computed`; они не дублируются в изменяемом состоянии. `watch` применяется только для реакции на изменение, которую нельзя выразить декларативно.
- Реактивный эффект не копирует состояние между источниками и не запускает неявный сетевой запрос. Загрузка, сохранение, уведомление, навигация и иные побочные эффекты находятся в именованной команде владельца сценария.
- Для конкурентных асинхронных действий определена семантика: актуален последний результат, повтор блокируется, действия выполняются последовательно или параллельно. Отмена, очистка и обработка ошибки не оставляют состояние в неопределённом виде.

## API и DTO

- API-клиент выполняет запрос, передаёт типизированные данные, проверяет внешнюю форму и возвращает результат без зависимости от Vuetify, компонентов, Pinia или маршрутов.
- DTO и параметры запроса имеют одну нормативную форму в API-слое. UI не собирает HTTP-путь, заголовки и технический формат запроса.
- Маппер чистый и детерминированный; сетевые вызовы, состояние, навигация и уведомления остаются у их владельцев.

## Тестируемость и приёмка

- Изменение сохраняет возможность изолированно проверить предметную логику, преобразование DTO, состояние и поведение компонента через явные входы и наблюдаемый результат.
- Исправление дефекта сопровождается регрессионным тестом, который воспроизводит исправленное условие и не проходит без исправления.
- До приёмки выполнены применимые к изменению проверки, настроенные в `back-office`: форматирование, статический анализ, проверка типов, модульные или компонентные тесты. Команды берутся из фактической конфигурации приложения; отсутствующие команды не предполагаются.
- Изменённое использование API Vue, Vuetify, Pinia, Vite, TypeScript и иных библиотек сверено через Context7 с версией из manifest или lock-файла; если Context7 не покрывает вопрос, используется официальная документация.
- Приёмка включает проверку границ импортов, отсутствия неявных подстановок для изменённого сценария и соответствия этого документа фактической реализации.
- Проверка diff подтверждает отсутствие несвязанных изменений и соответствие этого документа фактическому коду, контракту, конфигурации и тестам, включая размещение типов и констант по этому правилу.
