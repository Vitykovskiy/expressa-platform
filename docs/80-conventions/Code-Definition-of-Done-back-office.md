# Definition of Done для production-кода back-office

> **КРИТИЧНО: Приоритет содержательного результата.** Критерии DoD применяются, когда изменение приносит проверяемую пользу: уточняет ответственность, контракт, зависимость, поведение или сопровождаемость. Формальная правка формы, имени или расположения без такой пользы не требуется.

Документ определяет готовность production-кода автономного PWA `back-office` на Vue 3, Vuetify, TypeScript, Vite и Pinia. Он применяется к новой реализации, изменению и приёмке кода приложения; требования к продуктовым сценариям, поставке и инфраструктуре находятся вне этой ноты. Границы приложения и рекомендуемая структура определены в [Архитектуре клиентов](../20-architecture/Client-architecture.md) и [Границах приложений](../20-architecture/Repository-boundaries.md).
Для всего UI-кода обязательны [UI DoD](../40-quality/Definition-of-done.md),
[стиль Vue-кода](../40-quality/Vue-code-style.md),
[контракт UI back-office](../../back-office/docs/10-architecture/ui-ownership.md) и
[стратегия проверки](../40-quality/Validation-strategy.md).

[ADR-011](../20-architecture/ADR/ADR-011-back-office-clean-slate.md) освобождает
проектирование UI от прежней визуальной формы. Все технические требования
этого DoD сохраняются: стек, code-style, слои, контракты и границы ответственности.
Сходство со старым интерфейсом не является критерием готовности.

## Обязательная приёмка чистого кода

Общие [критерии чистого кода](Clean-code.md) являются частью этого DoD:
KISS, DRY, все пять SOLID и C1–C6 обязательны в применимой области.
Review подтверждает их по изменённому коду и затронутым потребителям согласно
[правилам приёмки](Clean-code.md#приёмка-изменения). Неприменимость обоснована;
нарушение или непроверенный применимый критерий блокируют положительный
вердикт. Успех форматирования, lint, typecheck или сборки их не заменяет.
Контурные требования ниже действуют совместно с общим стандартом.

## Простота и ответственность

- Код добавляется для текущего достижимого сценария. Неиспользуемые параметры, поля, ветки, функции, файлы и оболочки не остаются в production-коде.
- Общая абстракция допустима для нескольких существующих потребителей, когда она проще отдельных реализаций. Одноразовая форма не получает отдельный тип или helper, если вывод TypeScript сохраняет понятный контракт.
- Функция имеет предметное имя, понятные входы и одну связную ответственность. Основной сценарий читается линейно; самостоятельный шаг выносится только когда это проясняет назначение, инвариант или тестирование.
- Комментарий объясняет неочевидное решение или существенный инвариант, а не пересказывает код.
- Форматтер Prettier с корневой конфигурацией и локальный линтер ESLint обязательны. Изменённый код разделён пустыми строками на логические блоки по [правилам форматирования и читаемости](../40-quality/Vue-code-style.md#форматтер-линтер-и-пустые-строки); успешный запуск форматтера не заменяет это требование. При создании конфигурации нового клиента включаются указанные там правила пустых строк.

## SOLID, DRY и KISS на ревью

- SOLID: модуль имеет одну связную ответственность, явный контракт и владельца состояния. Замена реализации сохраняет контракт потребителя; обратные импорты и скрытое изменение чужого состояния недопустимы. Принцип не требует обязательных классов или интерфейсов без потребителя.
- DRY: предметная норма и преобразование DTO имеют одного владельца. Общий код выделяется для существующих потребителей; несвязанные действия не объединяются условными ветками или расширением публичного API ради сходства реализации.
- KISS: каждый элемент нужен текущему достижимому сценарию; путь данных, ошибки и эффекты понятны. Не добавляются каркасы, wrappers и конфигурация на будущее. Обоснование проверяется по коду, потребителям и контрактам, без новых метрик или инструментов.

## Типы и внешние данные

- `any` не используется. Внешние данные считаются недоверенными до проверки их формы и обязательных значений на границе приложения.
- DTO описывает контракт обмена с API и не подменяет модель, которую используют компоненты и состояние. Преобразование DTO в модель является явной, чистой операцией без UI, состояния и сетевых побочных эффектов.
- Каждый файл имеет одну зону ответственности. Все именованные `type`, `interface`, `enum` и другие контракты располагаются в соседнем `*.types.ts`; все константы уровня модуля, предметной области и конфигурации — в соседнем `*.constants.ts`. Файл реализации содержит только исполняемое поведение и не смешивается с объявлениями типов и констант. Локальные выводимые типы и значения внутри функции допустимы, если принадлежат только её алгоритму. Тест может хранить данные, типы и константы, используемые только этим spec; общие тестовые контракты и данные выносятся отдельно.
- Отсутствующее значение допускается только как явное состояние модели и обрабатывается отдельной веткой. Код не подставляет другое поле, формат, текст или значение по умолчанию для продолжения работы с недостоверными данными.
- Ошибка контракта и ошибка запроса имеют явное, безопасное для UI состояние. Альтернативная форма данных допустима только как явно определённая часть контракта.

## Слои и зависимости

Целевая структура — `app`, `layouts`, `modules`, `shared` по
[ADR-015](../20-architecture/ADR/ADR-015-back-office-domain-structure.md).
`app` владеет запуском и межпредметной композицией; `layouts` — общим
представлением каркаса и навигации; `modules/<область>` — страницами,
состоянием, API и дочерним представлением одной бизнес-области;
`shared` — только локальными техническими и переиспользуемыми UI-примитивами.
Глобальные `pages`, `widgets`, `features`, `entities` в целевой структуре
не используются. Отдельные обязанности файлов и владельцы состояния сохраняются.

ADR-015 проходит независимое review до зависимого переноса. До переноса
[локальная карта](../../back-office/docs/80-conventions/code-layout.md)
описывает фактические пути; новая норма не подтверждает готовность реализации
или пользовательскую приёмку. Исторические правила ADR-013/014 заменяются
только в явно указанной ADR-015 части.

- По ADR-016 Vue Router records выбирают пять page components; RouterView выводит
  matched component. Title/access принадлежат metadata; role gate предшествует
  mount/read. Root и unknown application paths redirect home; business-query
  validation не выбирает страницу. Bootstrap сохраняет persistent App/session.
- `app` импортирует layouts, modules и shared; layouts — собственные контракты/assets
  и shared. Сторонний RouterLink разрешён для anchors по ADR-016; app router singleton
  не импортируется. Layout не импортирует app, modules, stores, HTTP или native controllers.
- Module импортирует собственные файлы и shared. Существующие зависимости auth,
  UsersRoute и notifications от session разрешены в точных границах ADR-015;
  session не импортирует потребителей. Новая связь соседних областей не возникает
  ради переноса; межпредметную координацию собирает app. Новые runtime-циклы запрещены.
- Код размещается у самого узкого владельца ответственности. Существующее дочернее
  представление находится в `components` своей области; обязательные `api/model/ui`
  и пустые каталоги на будущее не создаются. Перенос в shared обоснован несколькими
  существующими потребителями внутри back-office.
- `shared` не зависит от app/layouts/modules, предметных DTO, моделей и состояния.
  Прямые импорты, соседние типы/константы и границы API/store/presentation сохраняются.
- `back-office` автономен: запрещены импорты исходного кода, типов, компонентов, конфигурации и тестовых артефактов из `front-office`.

## Компоненты, composables и Pinia

- Компонент отвечает за представление и пользовательские события. Он получает явные `props`, сообщает действия через `emits` и не скрывает загрузку данных или владение состоянием в представлении.
- Компонент-контейнер собирает страницу или блок; отображающий компонент не обращается к API и не меняет состояние другой пользовательской области.
- Composable выделяется для повторно используемого связного поведения. Его возвращаемый контракт минимален и понятен; одноразовая локальная реактивная логика остаётся рядом с владельцем.
- Store Pinia владеет состоянием и прикладными командами своей области. Store не становится прокси для API: сетевой контракт остаётся в локальном API-слое, а преобразование DTO не смешивается с изменением состояния.
- Состояние меняется только через владельца: публичный контракт не раскрывает изменяемые внутренние ссылки, если потребителю достаточно чтения или команды.

## Реактивность и побочные эффекты

- Производные значения выражаются через `computed`; они не дублируются в изменяемом состоянии. `watch` применяется только для реакции на изменение, которую нельзя выразить декларативно.
- Реактивный эффект не копирует состояние между источниками и не запускает неявный сетевой запрос. Загрузка, сохранение, уведомление, навигация и иные побочные эффекты находятся в именованной команде владельца сценария.
- Для конкурентных асинхронных действий определена семантика: актуален последний результат, повтор блокируется, действия выполняются последовательно или параллельно. Отмена, очистка и обработка ошибки не оставляют состояние в неопределённом виде.

## API и DTO

- API-клиент выполняет запрос, передаёт типизированные данные, проверяет внешнюю форму и возвращает результат без зависимости от Vuetify, компонентов, Pinia или маршрутов.
- DTO и параметры запроса имеют одну нормативную форму в API-слое. UI не собирает HTTP-путь, заголовки и технический формат запроса.
- Маппер чистый и детерминированный; сетевые вызовы, состояние, навигация и уведомления остаются у их владельцев.

## Тестируемость и приёмка

- Изменение сохраняет возможность изолированно проверить предметную логику, преобразование DTO, состояние и поведение компонента через явные входы и наблюдаемый результат.
- До явной приёмки результата пользователем автоматизированные тесты не создаются, не изменяются и не запускаются; они не входят в pre-commit, pre-push, CI или deployment-gate. После приёмки тесты допустимы только по прямому запросу пользователя.
- До приёмки выполнены применимые нетестовые проверки, настроенные в `back-office`: форматирование, статический анализ, проверка типов и сборка. Команды берутся из фактической конфигурации приложения; отсутствующие команды не предполагаются.
- Изменённое использование API Vue, Vuetify, Pinia, Vite, TypeScript и иных библиотек сверено через Context7 с версией из manifest или lock-файла; если Context7 не покрывает вопрос, используется официальная документация.
- Приёмка включает проверку границ импортов, отсутствия неявных подстановок для изменённого сценария и соответствия этого документа фактической реализации.
- Проверка diff подтверждает отсутствие несвязанных изменений и соответствие этого документа фактическому коду, контракту и конфигурации, включая размещение типов и констант по этому правилу.

## UI и каталог

Видимые изменения проходят [UI DoD](../40-quality/Definition-of-done.md)
и [процесс визуальной работы](../40-quality/Validation-strategy.md#процесс-визуальной-работы),
включая осмотр целого экрана после последних правок и независимую проверку.
Storybook и иные каталоги выбираются по UI-задаче согласно ADR-011.
Наличие каталога или успешная сборка не принимают дизайн или полноту сценария.
