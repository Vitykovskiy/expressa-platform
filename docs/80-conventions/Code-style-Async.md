# Асинхронные сценарии

Применяется к новому и изменяемому авторскому коду по [общему стандарту](Clean-code.md). Приёмка — [общий DoD](Definition-of-Done.md).

## Политика запуска и завершения

Для конкурентных запусков определены актуальность последнего результата,
блокировка повтора, очередь либо независимость. Политику выбирает владелец
сценария; отмена и cleanup не заменяют её. Поздние данные, ошибки,
завершение загрузки и уведомления не применяются к новому контексту.
Данные запуска связаны с его контекстом; изменяемый черновик не читается
позднее как прежний снимок. Копия каждого объекта автоматически не создаётся.

Гарантии отмены и завершения проверяются по реальному источнику, а не имени
API. Отмена клиентского запроса не обещает откат серверной записи; повтор
мутации следует её предметной семантике. Однопоточный JavaScript не исключает
устаревший результат через асинхронную границу. Составной инвариант и
атомарность обеспечивает владелец общего ресурса; клиентская очередь
не заменяет серверную транзакцию.

Если уже используется очередь или ограниченный ресурс, определены порядок,
освобождение и завершение ожидания. Ошибка, отмена и повтор не создают
циклического или бесконечного ожидания. Новые locks, retries, timeout,
workers и счётчики не вводятся без текущего контракта.

## Наблюдение при приёмке

Сопоставьте быстрые повторные запуски, поздние success/error, loading и завершение владельца с выбранной политикой. Чтение исходника подтверждает механизм, но не наблюдение runtime. Несогласованная политика повтора или применение завершения к чужому контексту блокируют приёмку.

## Пример позднего чтения

**Учебная иллюстрация, не API Expressa.** Существующее чтение возвращает проверенное название либо ошибку; задана политика «актуален последний выбранный ID». Антипример запускает A, затем B и безусловно публикует каждое завершение. Если B заканчивается раньше A, экран снова показывает A; поздняя ошибка A также может закрыть успешный B, а завершение A — снять loading B.

Исправление использует подтверждённую отмену либо существующую защиту актуальности у владельца. При запуске B прежний контекст отзывается, его данные/ошибка очищаются по контракту; только B вправе публиковать success, error и окончание загрузки. При завершении владельца работа прекращается. Проверяются реальные гарантии источника, включая синхронную ошибку запуска; отмена не становится пользовательским сбоем. Идентификатор или счётчик не добавляется как универсальный рецепт.

## Пример мутации и повтора

**Учебная иллюстрация.** Для сохранения задано игнорирование повтора до завершения. Антипример при втором нажатии отменяет клиентское ожидание первой записи и немедленно запускает вторую: сервер мог уже принять первую. Это нарушает заданную политику и не доказывает откат.

Исправление у существующего владельца допускает одну операцию, сохраняет необходимые данные запуска и не принимает повтор до её завершения. Успех и ошибка завершают занятость, ошибка остаётся явным результатом, следующий запуск после завершения разрешён. Очередь или параллельные записи потребовали бы другого предметного требования. Атомарность составной серверной записи проверяется у backend-транзакции по [backend DoD](Code-Definition-of-Done-backend.md#контракты-ошибки-и-побочные-эффекты), а не по клиентской занятости.
