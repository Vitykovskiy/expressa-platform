# Как пользоваться документацией

Документация предназначена для разработчиков и AI-агентов. Начните с [корневого README](../../README.md) и [карты системы](../INDEX.md), затем читайте только ветви задачи. Краткий вход для агента — [llms.txt](../../llms.txt); он не заменяет инструкции.

## Порядок чтения

1. Примените актуальные инструкции пользователя и иерархию `AGENTS.md` до рабочего каталога.
2. Определите затронутые контуры, предмет, действие и среду. Неизвестные признаки не подменяйте предположениями.
3. Выберите маршрут в `docs/INDEX.md` системы или каждого затронутого приложения. Для разработки добавьте [индекс требований](../80-conventions/INDEX.md).
4. Переходите в более узкие `INDEX.md`. Для сквозного вопроса используйте `_MOC-*.md` как последовательность дополняющих источников.
5. Найдите точный runtime-объект в `COVERAGE.md` соответствующего контура и откройте его основную ноту.
6. Прочтите первичные источники изменяемого утверждения. Для ожидаемого и фактического поведения нужны и контракт, и реализация.
7. При смене области, этапа, среды или требования обновите применимую часть контекста по [агентной системе](../80-conventions/Agent-system.md).

`rg` помогает найти точный идентификатор после выбора области. Совпадение текста не делает найденный файл нормативным источником. Если маршрут отсутствует, отметьте пробел и найдите первичный источник; не считайте соседнюю ноту владельцем по умолчанию.

## Роли документов

Роль задаётся полем `knowledge_role`. Она описывает назначение документа, а не подтверждает реализацию или приёмку.

| Значение         | Как использовать                                                                   |
| ---------------- | ---------------------------------------------------------------------------------- |
| `navigation`     | Выбрать источник; карта не устанавливает поведение.                                |
| `requirements`   | Найти действующую норму в её области; выполнение требует отдельного подтверждения. |
| `implementation` | Читать описание реализации вместе с указанными кодом, схемой или конфигурацией.    |
| `decision`       | Прочитать статус ADR и ограничения замещения.                                      |
| `operations`     | Выполнить поддерживаемую операцию с её предусловиями.                              |
| `planning`       | Узнать план или трассировку; не выводить текущий статус из карточки.               |
| `registry`       | Найти объект и владельца знания; существующий тест не означает успешный прогон.    |
| `history`        | Разобрать прошлое состояние; не выполнять старую команду как актуальную.           |
| `source`         | Прочитать исходный материал с действующими поправками и ADR.                       |

В одной ноте могут соседствовать требование и наблюдение. Такие части имеют явные заголовки или маркировку; роль документа не меняет [приоритет источников](Source-precedence.md). Оперативное `state.yaml` и отчёты задачи — состояние процесса, а не контракт продукта.

## Метаданные и актуальность

Формат и поля определены в [соглашениях](Naming-conventions.md). `last_verified` — дата последней указанной проверки, не срок годности и не гарантия runtime. Редактор не обновляет её после одного форматирования. `status` ADR, `implementation_status` сценария и статус процесса обозначают разные вещи.

Бэклог и журналы читаются по отдельному запросу о планировании или истории. Снимки в `_sources` сохраняются как первичные материалы; текущие контракты не копируются из них без учёта принятых решений.

## Минимальный контекст

Для узкой задачи достаточно применимых правил, выбранной ноты, её первичных источников и зависимостей. Не загружайте целиком бэклог, все `COVERAGE.md` или OpenAPI ради одного символа. Для межконтурной задачи объедините маршруты всех затронутых приложений.

Каждая предметная нота объясняет одну концепцию, контракт, процедуру или решение. Подробная норма имеет одного владельца; остальные страницы ссылаются на него. Изменённые факты и ссылки проверяются по [протоколу обновления](Update-protocol.md).
