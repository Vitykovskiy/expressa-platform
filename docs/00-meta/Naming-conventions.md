# Формат документации

## Файлы и ссылки

- Документы пишутся в Markdown на русском языке; идентификаторы кода, API, поля и команды сохраняются точно.
- `README.md` объясняет назначение каталога и ведёт к его карте. Раздел `Структура каталога` — первый H2, сразу за ним следует дерево `text`: этот формат проверяет [существующий checker](../../scripts/check-docs.mjs).
- `INDEX.md` маршрутизирует задачи внутри раздела. `_MOC-*.md` связывает дополняющие источники сквозного вопроса и не повторяет каталог раздела.
- Предметные файлы имеют понятное имя по концепции. При правке сохраняйте существующий путь; переименование требует обновления всех зависимых ссылок.
- Ссылки — относительные Markdown-ссылки на конкретный файл с расширением. Для раздела используйте существующий якорь. Obsidian wikilinks и абсолютные локальные пути не используются.
- ADR продолжают существующую нумерацию и структуру своего каталога. Заменённые решения сохраняются с явным статусом и ссылкой на замену.

## Метаданные

Текущие предметные ноты содержат YAML frontmatter. Навигация и планирование используют те же поля по применимости.

| Поле             | Значение                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `title`          | Название документа, согласованное с H1.                                                                                 |
| `type`           | Вид: контракт, feature, ADR, guide, index и другие существующие виды.                                                   |
| `knowledge_role` | Назначение из [таблицы ролей](How-to-use-this-vault.md#роли-документов).                                                |
| `owner`          | Владелец знания: `root`, `backend`, `front-office`, `back-office`.                                                      |
| `scope`          | Контур или общая система `system`; у плановой карточки — область её каталога.                                           |
| `last_verified`  | Дата проверки утверждений по указанным источникам; не обновляется механически. Обязательна для текущей предметной ноты. |
| `sources`        | Пути первичных источников относительно документа. Обязательны для текущей предметной ноты.                              |

`status`, `superseded_by`, `implementation_status`, `requirements`, `repositories`, `related`, `tags`, `area`, `updated` и `description` сохраняются, когда несут отдельный смысл. `updated` обозначает редактирование, а не проверку. У старой карточки без проверки не добавляйте выдуманную дату. Не переписывайте снимок исходного ТЗ ради этих полей.

## Самостоятельный раздел

Используйте один H1 и последовательные H2/H3 с предметными названиями. Нумерация исходного ТЗ остаётся в снимке; в текущих нотах заголовок описывает содержание. Объясните актор, условия, требуемый результат или наблюдаемую границу. Для команды укажите рабочий каталог, предусловия и ожидаемую ошибку, если она существенна.

Пример берётся из действующего контракта. Точные HTTP-схемы принадлежат OpenAPI, структура данных — `schema.sql`: не создавайте параллельные полные копии. Незавершённую реализацию обозначайте как требование или пробел, а не обещание «скоро».
