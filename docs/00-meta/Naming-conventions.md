# Формат документации

## Файлы и ссылки

- Документы пишутся в Markdown на русском языке; идентификаторы кода, API, поля и команды сохраняются точно.
- `README.md` объясняет назначение каталога и ведёт к его карте. Раздел `Структура каталога` — первый H2, сразу за ним следует дерево `text`: этот формат проверяет [существующий checker](../../scripts/check-docs.mjs).
- `INDEX.md` маршрутизирует задачи внутри раздела. `_MOC-*.md` связывает дополняющие источники сквозного вопроса и не повторяет каталог раздела.
- Предметные файлы имеют понятное имя по концепции. При правке сохраняйте существующий путь; переименование требует обновления всех зависимых ссылок.
- Ссылки — относительные Markdown-ссылки на конкретный файл с расширением. Для раздела используйте существующий якорь. Obsidian wikilinks и абсолютные локальные пути не используются.
- ADR продолжают существующую нумерацию и структуру своего каталога. Заменённые решения сохраняются с явным статусом и ссылкой на замену.

## Метаданные

Текущие предметные ноты содержат YAML frontmatter. Навигация и планирование используют те же поля по применимости.

| Поле             | Значение                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `title`          | Название документа, согласованное с H1.                                                                                 |
| `type`           | Вид: контракт, feature, ADR, guide, index и другие существующие виды.                                                   |
| `knowledge_role` | Назначение из [таблицы ролей](How-to-use-this-vault.md#роли-документов).                                                |
| `owner`          | Владелец знания: `root`, `backend`, `front-office`, `back-office`.                                                      |
| `scope`          | Контур или общая система `system`; у плановой карточки — область её каталога.                                           |
| `last_verified`  | Дата проверки утверждений по указанным источникам; не обновляется механически. Обязательна для текущей предметной ноты. |
| `sources`        | Пути первичных источников относительно документа. Обязательны для текущей предметной ноты.                              |

`status`, `superseded_by`, `implementation_status`, `requirements`, `repositories`, `related`, `tags`, `area`, `updated` и `description` сохраняются, когда несут отдельный смысл. `updated` обозначает редактирование, а не проверку. У старой карточки без проверки не добавляйте выдуманную дату. Не переписывайте снимок исходного ТЗ ради этих полей.

## Самостоятельный раздел

Используйте один H1 и последовательные H2/H3 с предметными названиями. Нумерация исходного ТЗ остаётся в снимке; в текущих нотах заголовок описывает содержание. Объясните актор, условия, требуемый результат или наблюдаемую границу. Для команды укажите рабочий каталог, предусловия и ожидаемую ошибку, если она существенна.

Пример берётся из действующего контракта. Точные HTTP-схемы принадлежат OpenAPI, структура данных — `schema.sql`: не создавайте параллельные полные копии. Незавершённую реализацию обозначайте как требование или пробел, а не обещание «скоро».

## Область проверки документации

Из корня репозитория запускается существующий инструмент:

```sh
node scripts/check-docs.mjs
```

Он работает без сети, читает локальные файлы и список tracked README через Git,
накапливает структурные нарушения и возвращает ненулевой статус при ошибках.
`--scope` выбирает контур, `--sample` ограничивает только проверку наличия
первичных источников. Структура tracked вложенных README проверяется глобально
даже при выборе одного контура. Ссылки по якорям и внешние URL не проверяются;
успешный запуск не доказывает актуальность содержания, семантику источников,
соответствие runtime или пользовательскую приёмку.

В README после первого H2 `Структура каталога` ожидается непустое дерево
в блоке `text` с тройными обратными кавычками. Если после заголовка только
пустые строки или конец файла, инструмент сообщает об отсутствии дерева.
В COVERAGE каждый поддерживаемый путь к коду из каждой ячейки — Markdown-ссылка
или путь в одинарных обратных кавычках — учитывается после нормализации;
повторы объединяются. Одна ячейка может описывать несколько исходных файлов.

Для backend ожидается `backend/openapi/openapi.json`, для клиентов —
`front-office/contracts/openapi.json` и `back-office/contracts/openapi.json`.
Отсутствие, ошибка чтения, некорректный JSON, документ не в форме объекта или
поле `paths` не в форме объекта становятся явными диагностическими ошибками.
Пустой объект `paths` допустим. Для root вход OpenAPI неприменим.
Это не полная валидация схемы OpenAPI: остальные свойства и методы endpoints
этот инструмент не проверяет.

### Поддерживаемое подмножество синтаксиса

Инструмент использует ограниченные извлекатели, а не полноценные парсеры
CommonMark и YAML. Эти границы описывают проверку, а не сужают нормативный
формат документации:

- Из извлечения ссылок исключаются простые блоки с тройными обратными
  кавычками в начале строки и однострочный код в одинарных обратных кавычках.
  Блоки с тильдами, более длинными ограждениями и сложные варианты inline-кода
  могут разбираться неполно; инструмент не гарантирует корректное исключение
  их содержимого.
- Поддерживаются простые встроенные Markdown-ссылки. Сложные вложенные
  конструкции, reference-style links и общий синтаксис экранирования
  не покрыты полноценным Markdown-разбором. Вики-ссылки распознаются для
  диагностики их запрета, а не становятся разрешённым форматом.
- Frontmatter извлекается из начального блока `---` как простые строки
  `key: value` и следующие за ключом строки списка `- item`.
  Произвольные вложенные YAML-структуры, anchors, aliases и многострочные
  значения не валидируются как YAML. Наличие извлечённого поля не доказывает
  правильность его содержимого.
- COVERAGE разбирается как простая таблица с разделителем `|`; учитываются
  разделители в вики-ссылках, но общего разбора экранированных `|` и pipes
  внутри inline-кода нет. Успех не означает поддержку любой допустимой
  Markdown-таблицы.

Сложные конструкции и смысл документа проверяют отдельно по первичным
источникам. Режим `--self-test` является отдельным тестовым режимом и не
входит в обычный запуск; ограничения тестов задаёт корневой AGENTS.
