# Expressa MVP — техническое задание

**Версия:** 2.0  
**Дата:** 24 июля 2026 года  
**Статус:** готово к оценке и реализации  
**Назначение:** каноническое продуктовое и техническое основание для трёх автономных репозиториев Expressa

## 1. Основание и цель

Expressa — два устанавливаемых прогрессивных веб-приложения (PWA): мобильное приложение для оформления заказа в кофейне-киоске и рабочее приложение для сотрудников.

MVP обеспечивает полный контур:

1. клиент просматривает меню;
2. клиент проходит телефонную авторизацию;
3. клиент формирует корзину и оформляет заказ;
4. бариста принимает заказ, готовит его и отмечает готовность к выдаче;
5. клиент оплачивает заказ на кассе при получении;
6. после получения оплаты сотрудник выдаёт заказ;
7. клиент видит состояние и историю собственных заказов;
8. администратор управляет меню, ценами и доступностью.

## 2. Зафиксированные организационные решения

### 2.1. Репозитории

Система состоит из трёх автономных репозиториев:

| Репозиторий | Назначение | Основной стек |
|---|---|---|
| `backend` | API, бизнес-логика, данные, авторизация, аудит | NestJS, TypeScript, PostgreSQL |
| `front-office` | Клиентское мобильное PWA | Vue 3, Vuetify, TypeScript, Vite |
| `back-office` | Рабочее PWA бариста и администратора | Vue 3, Vuetify, TypeScript, Vite |

Каждый репозиторий содержит собственные зависимости, типы, компоненты, конфигурацию, тесты, документацию и конвейер поставки.

Межрепозиторное взаимодействие проходит через версионированный HTTP API. Backend публикует OpenAPI-контракт. Каждый клиент хранит собственный зафиксированный снимок контракта и собственный сгенерированный либо вручную реализованный API-клиент.

### 2.2. Управление пакетами

Во всех репозиториях применяется `npm`.

Обязательные артефакты:

- `package.json`;
- `package-lock.json`;
- фиксированная LTS-версия Node.js;
- команды `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`;
- проверка целостности lock-файла в CI.

### 2.3. Документация

Документация каждого репозитория организована как связанная база знаний в `docs/`, совместимая с Obsidian. Корневой `README.md` служит короткой точкой входа: объясняет назначение репозитория, запуск, основные команды и ведёт к `docs/INDEX.md`.

База знаний строится по следующим правилам:

- одна нота описывает одну концепцию, поведение, контракт или архитектурное решение;
- `docs/INDEX.md` служит главной картой, а `_MOC-*.md` — картами отдельных разделов;
- каждая нота содержит метаданные `title`, `description`, `type`, `area`, `status`, `tags` и `updated`;
- связи между нотами оформляются через `[[wikilink]]`, ссылки на код и внешние источники — обычными Markdown-ссылками;
- `docs/00-meta/` фиксирует правила использования базы знаний, именования нот, протокол обновления и словарь терминов;
- код, OpenAPI, конфигурация и тесты имеют приоритет над текстом документации;
- `docs/00-meta/Update-protocol.md` определяет, какие ноты обновляются при каждом типе изменения кода;
- затронутые ноты обновляются вместе с кодом в том же pull request.

Общий каркас для трёх репозиториев:

| Путь | Назначение |
|---|---|
| `docs/README.md` | Назначение базы знаний и ссылка на главную карту |
| `docs/INDEX.md` | Главная карта документации |
| `docs/00-meta/` | Правила использования, именования и обновления, словарь |
| `docs/10-overview/` | Обзор проекта, запуск и стек |
| `docs/20-architecture/` | Архитектура и `ADR/` с записями архитектурных решений |
| `docs/70-deployment/` | Окружения, сборка, поставка и восстановление |
| `docs/80-conventions/` | Инженерные соглашения |
| `docs/95-testing/` | Стек, уровни, паттерны и покрытие тестами |
| `docs/_journal/` | Краткие записи о существенных изменениях |
| `docs/_sources/` | Зафиксированные исходные контракты и другие внешние источники, если они нужны репозиторию |

Предметные разделы адаптируются к ответственности репозитория:

| Репозиторий | Разделы |
|---|---|
| `front-office`, `back-office` | `30-core-layer/` — инфраструктура клиента; `40-features/` — пользовательские области; `50-api-integration/` — использование backend API и зафиксированного снимка OpenAPI из `docs/_sources/`; `60-ui-kit/` — компоненты, токены, темы и адаптивность |
| `backend` | `30-platform/` — общая серверная инфраструктура; `40-domain-modules/` — бизнес-модули; `50-http-api/` — публичный HTTP API; `60-data-and-integrations/` — хранение данных и внешние интеграции |

Раздел `90-agents/` создаётся только при наличии проектных инструкций или рабочих процессов агентов. Он ссылается на их первичные файлы и не становится вторым источником истины.

## 3. Состав MVP

1. Меню: категории, товары, размеры напитков `S`, `M`, `L`, добавки, цены и доступность.
2. Телефонная авторизация.
3. Корзина и оформление заказа.
4. Оплата на кассе при получении.
5. Этапы заказа: оформлен, принят, готовится, готов, выдан.
6. Клиентское PWA `front-office`.
7. Рабочее PWA бариста и администратора `back-office`.
8. Управление меню, ценами, доступностью и заказами.
9. История заказов клиента и повтор заказа.
10. Push-уведомления клиенту о стадиях `Принят`, `Готов` и `Выдан`, бариста — о новом заказе.

## 4. За рамками MVP

- онлайн-эквайринг и предоплата;
- бонусы, уровни, скидки, купоны и программа лояльности;
- временные слоты, лимиты слотов и предварительный выбор времени;
- доставка;
- несколько филиалов;
- складской учёт и автоматическое списание остатков;
- аналитические панели и финансовая отчётность;
- управление сотрудниками через интерфейс;
- клиентская отмена, возвраты и корректировка оплаты;
- уведомления о статусах через SMS или мессенджеры;
- акции и персональные предложения.

## 6. Пользовательские сценарии

### 6.1. Просмотр меню

1. Гость открывает front-office по публичной ссылке.
2. Приложение загружает состояние приёма новых заказов и меню.
3. Клиент выбирает категорию.
4. Клиент открывает товар.
5. Для напитка приложение заранее выбирает размер `M`, если он доступен, иначе — доступный размер напитка; для остальных товаров выбор размера отсутствует.
6. Приложение заранее выбирает обязательные добавки по умолчанию; клиент при необходимости меняет размер, добавки и количество.
7. Приложение показывает итоговую цену позиции.
8. Клиент добавляет позицию в корзину.

### 6.2. Авторизация и оформление

1. Клиент открывает корзину.
2. Приложение повторно проверяет состав и цены через backend.
3. Гость переходит к телефонной авторизации.
4. Клиент вводит номер телефона и одноразовый код.
5. Backend создаёт либо находит учётную запись customer.
6. Front-office сохраняет собранную до входа корзину и возвращает клиента к оформлению.
7. Клиент подтверждает оформление.
8. Backend создаёт заказ со стадией `Оформлен`.
9. Front-office открывает страницу текущего заказа.

### 6.3. Приготовление и выдача

1. Barista получает push-уведомление о новом заказе.
2. Back-office показывает новый заказ в очереди.
3. Barista переводит заказ в стадию `Принят`, клиент получает push-уведомление.
4. Barista переводит заказ в стадию `Готовится`.
5. Barista переводит заказ в стадию `Готов`, клиент получает push-уведомление.
6. Клиент оплачивает заказ на кассе.
7. После получения оплаты сотрудник нажимает `Выдать`.
8. Backend переводит заказ из стадии `Готов` в стадию `Выдан`, клиент получает push-уведомление.
9. Front-office показывает завершённый заказ в истории.

### 6.4. Повтор заказа

1. Клиент открывает выданный заказ в истории и нажимает `Повторить`.
2. Front-office проверяет состав старого заказа по текущему меню.
3. Доступные позиции переносятся в новую корзину с текущими ценами.
4. Позиции, которые больше нельзя собрать в прежней конфигурации, не переносятся; приложение показывает их клиенту.
5. Если текущая корзина не пуста, приложение запрашивает подтверждение её замены.
6. Front-office открывает подготовленную корзину для проверки и обычного оформления.

### 6.5. Управление меню

1. Administrator открывает раздел меню.
2. Administrator создаёт и упорядочивает категории.
3. Administrator создаёт напитки с одним или несколькими размерами из `S`, `M`, `L` и остальные товары без размеров.
4. Administrator задаёт цену каждого размера напитка либо единую цену товара без размера.
5. Administrator создаёт группы добавок и варианты добавок.
6. Administrator связывает группы добавок с категориями.
7. Administrator публикует элементы через признак активности.
8. Публичное меню отражает актуальную структуру.

### 6.6. Управление доступностью

1. Barista открывает раздел доступности.
2. Barista находит товар, размер напитка либо добавку.
3. Barista переключает оперативную доступность.
4. Backend применяет изменение атомарно и фиксирует автора.
5. Front-office получает актуальное меню при следующем запросе.
6. Backend повторно проверяет доступность при оформлении заказа.

## 7. Бизнес-правила

- **BR-001.** Публичное меню доступно гостю.
- **BR-002.** Оформление заказа требует подтверждённого номера телефона.
- **BR-003.** Сервер рассчитывает итоговую стоимость заказа.
- **BR-004.** Заказ хранит снимок названий, цен, добавок и размера напитка при его наличии на момент оформления.
- **BR-005.** Клиент оплачивает заказ на кассе при получении.
- **BR-006.** После получения оплаты сотрудник переводит заказ из стадии `Готов` в стадию `Выдан`.
- **BR-007.** Выдача доступна для заказа на стадии `Готов`.
- **BR-008.** Изменение меню сохраняет историю ранее созданных заказов через снимки позиций.
- **BR-009.** Доступность проверяется при загрузке меню и при создании заказа.
- **BR-010.** Каждое действие сотрудника по заказу и доступности содержит автора и время.
- **BR-011.** Порядок стадий направлен вперёд: `Оформлен` → `Принят` → `Готовится` → `Готов` → `Выдан`.
- **BR-013.** Сотрудник может включить или выключить приём новых заказов. При выключении меню остаётся доступным, оформление блокируется, а ранее созданные заказы продолжают обрабатываться.
- **BR-014.** Валюта интерфейса — российский рубль. Денежные значения хранятся целым числом копеек.
- **BR-015.** Только напитки могут иметь один или несколько размеров из `S`, `M`, `L`; остальные товары продаются по одной цене без выбора размера.
- **BR-016.** Клиент получает push-уведомления при переходе заказа в стадии `Принят`, `Готов` и `Выдан`.
- **BR-017.** Barista получает push-уведомление при создании нового заказа.
- **BR-018.** Отказ от push-уведомлений не ограничивает оформление и обработку заказа.
- **BR-019.** Повтор заказа создаёт новую корзину по текущим ценам и доступности; снимок старого заказа остаётся неизменным.
- **BR-020.** Уникальная конфигурация позиции определяется товаром, размером для напитка и набором добавок.
- **BR-021.** Каждая обязательная группа добавок содержит бесплатный набор вариантов по умолчанию, который соответствует допустимому количеству выбранных вариантов.
- **BR-022.** Вход сохраняет текущую корзину, явный выход из учётной записи очищает её.
- **BR-023.** Для напитка по умолчанию выбирается доступный размер `M`; если его нет, выбирается доступный размер напитка. Карточка товара открывается с корректной конфигурацией.

## 8. Функциональные требования

### 8.1. Телефонная авторизация

- **FR-AUTH-001.** Система принимает российский номер телефона и приводит его к формату E.164.
- **FR-AUTH-002.** Система отправляет шестизначный одноразовый код через адаптер SMS-провайдера.
- **FR-AUTH-003.** Срок действия кода составляет 5 минут.
- **FR-AUTH-004.** Повторная отправка доступна через 60 секунд.
- **FR-AUTH-005.** Один код поддерживает до 5 попыток ввода.
- **FR-AUTH-006.** Успешная проверка создаёт customer при первом входе.
- **FR-AUTH-007.** Сессия использует короткоживущий access token и обновляемый refresh token.
- **FR-AUTH-008.** Refresh token хранится в защищённой HttpOnly-cookie и обновляется при использовании.
- **FR-AUTH-009.** Front-office восстанавливает сессию после перезагрузки страницы.
- **FR-AUTH-010.** Back-office допускает пользователей с ролью barista либо administrator.
- **FR-AUTH-011.** Выход завершает текущую сессию и отзывает refresh token.
- **FR-AUTH-012.** Среда `development` поддерживает фиксированный код через переменную окружения.

### 8.2. Меню

- **FR-CART-011.** Корзина, собранная до авторизации, сохраняется после успешного входа.

- **FR-ORD-005.** Начальная стадия заказа — `Оформлен`.
- **FR-ORD-007.** Заказ содержит снимки товара, добавок, количества, цен и размера напитка при его наличии.
- **FR-ORD-008.** Заказ содержит итоговую сумму в копейках.
- **FR-ORD-009.** Back-office показывает очередь с фильтрами по стадии и поиском по номеру.
- **FR-ORD-010.** Карточка заказа показывает состав, сумму, время, клиента и историю изменения стадий.

- **FR-AVL-008.** Перед созданием заказа система повторно проверяет доступность товаров, размеров и добавок. Недоступные позиции показываются клиенту.

## 10. Доменная модель

### 10.1. Основные сущности

|---|---|
| `User` | `id`, `phone`, `role`, `created_at`, `updated_at` |

Расшифровка неочевидных полей:

- `selection_type` — режим выбора вариантов добавок: `single` разрешает выбрать один вариант, `multiple` — несколько;
- `min_select` — минимальное количество вариантов, которое нужно выбрать в группе;
- `max_select` — максимальное количество вариантов, которое можно выбрать в группе;
- `is_default` — признак добавки, выбранной заранее;
- `is_active` — признак публикации элемента в меню;
- `is_available` — возможность заказать товар, размер напитка или добавку в текущий момент;
- `sort_order` — позиция элемента при отображении;
- поля с окончанием `_minor` хранят денежную сумму в целых копейках;
- `archived_at` — время архивирования элемента;
- snapshot-поля — сохранённые в заказе название, размер и цена на момент оформления;
- `payload` — дополнительные данные события.

### 10.2. Целостность

- номера телефонов уникальны после нормализации;
- порядок категории уникален среди активных категорий;
- порядок товара уникален внутри категории;
- тип товара принимает значения `DRINK` и `OTHER`;
- напиток содержит один или несколько размеров из `S`, `M`, `L`, каждый размер уникален внутри напитка;
- товар типа `OTHER` содержит одну цену и не имеет вариантов размера;
- опубликованный напиток содержит хотя бы один доступный размер; `M` выбирается по умолчанию, если доступен;
- минимальное количество выбранных добавок не превышает максимальное: `min_select ≤ max_select`;
- при `selection_type = single` используется `max_select = 1`;
- для обязательной группы требуется выбрать хотя бы одну добавку: `min_select ≥ 1`;
- количество доступных вариантов по умолчанию в обязательной группе находится между `min_select` и `max_select`, каждый такой вариант имеет нулевое изменение цены;
- цена товара, цена размера напитка и изменение цены добавки представлены целыми копейками;
- создание заказа и фиксация снимков выполняются одной транзакцией;

## 11. HTTP API

### 11.1. Общие правила

- базовый путь: `/api/v1`;
- формат: JSON UTF-8;
- идентификаторы: UUID;
- даты: ISO 8601 UTC;
- авторизация: Bearer access token;
- обновление сессии: HttpOnly refresh cookie;
- ошибки: единый объект `{ code, message, details, requestId }`;
- создание заказа использует заголовок `Idempotency-Key`;
- контракт: OpenAPI, формируемый backend в CI;
- совместимость: добавочные изменения внутри `/v1`, новый базовый путь для разрыва контракта.

### 11.2. Swagger и OpenAPI

- Swagger UI доступен по адресу `/docs`;
- OpenAPI JSON доступен по адресу `/docs/openapi.json`;
- в средах `local` и `development` доступны Swagger UI и OpenAPI JSON;
- в `local` и `development` дополнительная авторизация для доступа к документации не требуется;
- в `staging` и `production` Swagger UI и OpenAPI JSON отключены;
- публичные запросы можно выполнять через Swagger UI без токена;
- для защищённых запросов пользователь Swagger UI указывает Bearer access token с необходимой ролью;
- Swagger UI и OpenAPI JSON всегда описывают одну и ту же актуальную версию API.

## 12. Требования к front-office

### 12.1. Маршруты

| Путь | Экран |
|---|---|
| `/` | Меню |
| `/cart` | Корзина |
| `/auth/phone` | Ввод телефона |
| `/auth/code` | Ввод кода |
| `/orders/:id` | Текущий либо исторический заказ |
| `/orders` | История заказов |

### 12.2. Экран меню

- мобильная компоновка с категориями и карточками товаров;
- состояние приёма новых заказов в верхней части;
- быстрый переход к корзине с количеством и суммой;
- карточка напитка показывает цену от минимального размера, карточка остальных товаров — единую цену;
- визуальное состояние выключенной доступности;
- скелетон загрузки, пустое состояние и сообщение об ошибке;
- сохранение позиции прокрутки при возврате из карточки.

### 12.3. Карточка товара

- у напитка заранее выбран доступный размер: `M`, если он доступен, иначе — другой доступный размер; для остальных товаров элемент выбора размера отсутствует;
- выбор одной или нескольких добавок в зависимости от настроек группы;
- бесплатные варианты по умолчанию заранее выбраны во всех обязательных группах;
- пользователь может изменить размер и добавки в допустимых пределах;
- счётчик количества;
- динамический расчёт цены;
- интерфейс не позволяет оставить обязательную группу без минимального количества вариантов или превысить максимум;
- кнопка добавления в корзину доступна сразу после открытия опубликованного и доступного товара;
- состояние длинного названия и большого количества добавок.

### 12.4. Корзина

- список конфигураций;
- изменение количества;

## 18. Требования к качеству

### 18.1. Безопасность

- HTTPS во всех сетевых средах;
- точный список разрешённых origins;
- Secure, HttpOnly и SameSite для refresh cookie;
- ограничение частоты OTP и чувствительных API;
- хэширование OTP и refresh token;
- ролевые guard-проверки на backend;
- маскирование телефона и токенов в журналах;
- параметризованный доступ к данным через ORM;
- секреты через хранилище CI/CD и переменные окружения;
- журналирование действий сотрудников.

### 18.2. Производительность

- публичное меню: p95 ответа API до 500 мс при прогретой базе;
- операции заказа: p95 до 700 мс, исключая SMS;
- очередь back-office: первая загрузка до 2 секунд в тестовой сети;
- основной JavaScript front-office после сжатия: целевой бюджет до 300 КБ;

### 18.3. Доступность интерфейсов

- целевой уровень WCAG 2.1 AA;
- стандартная поддержка клавиатуры для форм и элементов управления; отдельные горячие клавиши не разрабатываются;
- видимый фокус;
- корректные подписи полей;
- контраст основных состояний;
- текстовые обозначения дополняют цветовые статусы;
- интерактивные зоны мобильного интерфейса от 44×44 px.

### 18.4. Надёжность

- транзакции для создания заказа и смены критических состояний;
- оптимистическая блокировка заказа;
- повторяемые миграции;
- ежедневная резервная копия PostgreSQL;
- проверка восстановления перед выпуском;
- health-check для backend и базы;
- управляемое завершение процесса;
- идемпотентность создания заказа;
- Ошибка отправки push-уведомления не препятствует изменению статуса заказа.

### 18.5. Наблюдаемость

- структурированные JSON-журналы;
- `requestId` во всех запросах и ошибках;
- идентификатор пользователя и заказа в релевантных событиях;
- метрики количества заказов по стадиям;
- метрики ошибок OTP и API;
- оповещение о недоступности readiness и росте ошибок 5xx;
- срок хранения эксплуатационных журналов задаётся конфигурацией.

### 18.6. Контрольные требования качества

- **Q-SEC.** API проходит проверку ролевого доступа, владения ресурсами, OTP, сессий, валидации входа, журналов и зависимостей; количество открытых находок уровней Critical и High равно 0.
- **Q-PERF.** Публичное меню, операции заказа и очередь укладываются в показатели раздела 18.2 на целевом наборе данных.
- **Q-DB.** Запросы публичного меню, очереди, истории и аудита используют подтверждённые индексы; количество N+1-запросов равно 0.
- **Q-UX.** Основные маршруты сохраняют отзывчивость на целевых мобильных и рабочих устройствах.
- **Q-A11Y.** Основные маршруты front-office и back-office соответствуют WCAG 2.1 AA по автоматическим и ручным проверкам.
- **Q-PRIVACY.** Телефоны, OTP и токены маскируются в журналах, ошибках и клиентских хранилищах согласно модели данных.
- **Q-BACKUP.** PostgreSQL получает ежедневную шифрованную резервную копию с контролем выполнения и политикой хранения.
- **Q-RESTORE.** Восстановление резервной копии проходит в изолированной среде и подтверждает согласованные RPO и RTO.
- **Q-OBS.** Метрики, панели и оповещения покрывают доступность сервисов, ошибки OTP, создание заказов и резервные копии.
- **Q-SMOKE.** Чистая база проходит миграции, seed и полный API-маршрут до выдачи заказа.
- **Q-E2E.** Сквозной браузерный сценарий связывает создание меню, клиентский заказ, приготовление, оплату, выдачу и историю.
- **Q-LOAD.** Нагрузочный профиль публичного меню, OTP, создания заказа, polling очереди и истории соответствует целевым p95 и error rate.
- **Q-RELEASE.** Выпуск фиксирует Git-теги и совместимые версии трёх репозиториев, соответствующие записи `CHANGELOG.md`, результаты обязательных проверок и процедуру миграции.

## 20. CI/CD и среды

### 20.1. Среды

- `local` — разработка конкретного репозитория;
- `development` — общий стенд команды с последними совместимыми версиями; front-office и back-office используют размещённый здесь backend без его локального запуска;
- `staging` — стабильный стенд для демонстрации текущего состояния и приёмки пользователем; сюда продвигаются только проверенные версии из `development`;
- `production` — рабочая среда кофейни; до завершения разработки и приёмки MVP не разворачивается.

### 20.2. Версионирование и журнал изменений

- backend, front-office и back-office имеют независимые версии по SemVer;
- до первого рабочего выпуска используются версии `0.x.y`, первый принятый выпуск MVP получает версию `1.0.0`;
- текущая версия сервиса хранится в поле `version` его `package.json`;
- формат `X.Y.Z` означает: `X` — несовместимые изменения, `Y` — новая обратно совместимая функциональность, `Z` — обратно совместимые исправления;
- выпуск обозначается Git-тегом `vX.Y.Z`, который соответствует версии `X.Y.Z` в `package.json`;
- тег создаётся на проверенном коммите основной ветки;
- корневой `CHANGELOG.md` содержит для каждой выпущенной версии дату и понятный список добавленных, изменённых и исправленных возможностей;
- changelog описывает значимые изменения выпуска и не повторяет список коммитов;
- CI прекращает выпуск, если версия в `package.json`, Git-тег и запись в `CHANGELOG.md` не соответствуют друг другу;
- сборка содержит версию сервиса и хеш коммита;
- Docker-образ выпуска получает тег `vX.Y.Z`; изменяемый тег `latest` не используется для `staging` и `production`;
- `development` автоматически обновляется из основной ветки и фиксирует хеш развёрнутого коммита;
- `staging` разворачивается только по Git-тегу версии;
- CI/CD сохраняет для `staging` точные версии трёх сервисов и идентификаторы развёрнутых Docker-образов;
- после запуска `production` получает те же Docker-образы, которые прошли проверку в `staging`, без повторной сборки.

Версии сервисов не обязаны совпадать. Совместимый набор может состоять, например, из backend `v0.5.0`, front-office `v0.7.1` и back-office `v0.4.2`.

## 21. Документация как часть задачи

Каждая задача обновляет соответствующие атомарные ноты в том же pull request. Точные связи между изменениями и нотами фиксируются в `docs/00-meta/Update-protocol.md` каждого репозитория.

Примеры связи:

| Изменение | Документация задачи |
|---|---|
| Новый endpoint | OpenAPI, нота в `50-http-api/` backend и, если клиент использует endpoint, затронутая нота в его `50-api-integration/` |
| Новая переменная окружения | Нота окружения в `70-deployment/` и `.env.example` |
| Новая миграция | Нота в `60-data-and-integrations/`; при изменении процедуры поставки — нота в `70-deployment/` |
| Новый UI-компонент | Storybook и нота в `60-ui-kit/` |
| Новый пользовательский сценарий | Нота в `40-features/` и затронутая нота в `95-testing/` |
| Новая эксплуатационная команда | Корневой `README.md` и затронутая нота в `70-deployment/` |
| Новое архитектурное решение | Новый ADR в `20-architecture/ADR/` |

## 22. Definition of Ready

Задача готова к разработке, когда содержит:

- связь с эпиком и требованиями;
- один основной результат;
- конкретный контур;
- критерии приёмки;
- зависимости;
- API-контракт либо ссылку на Storybook для интерфейсной задачи;
- тестовые сценарии;
- перечень документации, которую обновляет реализация;
- размер, подходящий для одного pull request либо явно разделённый на последовательные задачи.

## 23. Definition of Done

Задача завершена, когда:

- код проходит review;
- lint, typecheck, тесты и build проходят в CI;
- доменные правила покрыты автоматическими тестами;
- UI представлен актуальными stories;
- OpenAPI отражает актуальный backend-контракт;
- миграции применяются на чистой и рабочей тестовой базе;
- документация репозитория соответствует коду;
- ошибки содержат диагностический `requestId`;
- функциональность подтверждена в `development`, а версия для демонстрации — в `staging`;
- при выпуске версия в `package.json`, Git-тег и запись в `CHANGELOG.md` совпадают;
- критерии приёмки задачи выполнены.

## 25. Критерии приёмки MVP

1. Три репозитория разворачиваются и поставляются автономно.
2. Все команды используют npm и воспроизводимый lock-файл.
3. Storybook front-office и back-office используется как каталог UI до разработки бизнес-экранов.
4. Customer открывает меню, видит заранее выбранный доступный размер напитка и обязательные добавки, при необходимости меняет их, формирует корзину и авторизуется по телефону.
5. Backend проверяет цены и доступность и создаёт идемпотентный заказ.
6. Barista видит новый заказ и проводит его через все стадии.
7. После получения оплаты сотрудник переводит заказ из стадии `Готов` в стадию `Выдан`.
8. Customer видит текущий статус и историю.
9. Customer повторяет выданный заказ; корзина учитывает текущие цены и доступность.
10. Customer получает push-уведомления о стадиях `Принят`, `Готов` и `Выдан`.
11. Barista получает push-уведомление о новом заказе.
12. Administrator управляет категориями, товарами, размерами напитков, добавками и ценами.
13. Barista управляет доступностью и приёмом новых заказов.
14. Аудит содержит сотрудников и время критических действий.
15. Полный smoke-сценарий проходит на чистой базе, в `development` и `staging`.
16. CI каждого репозитория выполняет обязательные проверки.
17. Документация каждого репозитория соответствует выпущенному коду.
18. `staging` разворачивается только по Git-тегам версий и хранит точный набор версий трёх сервисов.
