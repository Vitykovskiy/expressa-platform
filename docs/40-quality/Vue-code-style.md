# Стиль Vue-кода

Это главный источник правил Vue и Vuetify для `back-office` и `front-office`.
Они обязательны для всего Vue-кода приложений.
Общие [критерии чистого кода](../80-conventions/Clean-code.md) действуют
совместно с этой нотой; [их приёмка](../80-conventions/Clean-code.md#приёмка-изменения)
обязательна для нового и изменяемого кода обоих клиентов.
Для back-office 2.0 эти правила сохраняются полностью.
[ADR-011](../20-architecture/ADR/ADR-011-back-office-clean-slate.md)
освобождает выбор визуальной формы, но не отменяет code-style, Vue/Vuetify
или [технический DoD](../80-conventions/Code-Definition-of-Done-back-office.md).
Продукты сохраняют собственные соглашения об именах и компоновке: Customer не
обязан использовать `Ui*`-имена или layout Admin.

## Компонент и шаблон

- **Область:** каждый SFC. **Правило:** используйте Composition API,
  `<script setup lang="ts">` и типизированные контракты; порядок блоков —
  `template`, `script`, `style`. **Исключение:** отсутствует только для
  совместимого внешнего кода, который не входит в задачу. **Проверка:**
  ревью SFC и `npm run typecheck`.
- **Область:** template. **Правило:** разметка остаётся декларативной; повторные
  или составные условия, фильтрация, сортировка, классы и presentation map
  выносятся в `computed` или типизированную карту представления. **Исключение:**
  простое чтение одного `props` или локального состояния допустимо в template.
  **Проверка:** ревью template и script.
- **Область:** условные и списочные блоки. **Правило:** `v-if` создаёт редко
  показываемый или дорогой блок, `v-show` сохраняет часто переключаемый блок;
  `v-if` и `v-for` не ставятся на один элемент, а список фильтруется в
  `computed`; каждый `v-for` имеет стабильный примитивный `:key`.
  **Исключение:** ключ-индекс допустим только для неизменяемого списка без
  локального состояния элементов. **Проверка:** ревью template.
- **Область:** объединения состояний. **Правило:** `switch` и presentation map
  покрывают каждый вариант union; тип карты привязан к union, а недостижимый
  вариант завершается проверкой `never`. **Исключение:** fallback допустим,
  когда вход действительно имеет внешний нетипизированный формат и рядом есть
  явная обработка ошибки. **Проверка:** `npm run typecheck` и ревью типов.

## Реактивность и границы компонентов

- **Область:** локальное состояние. **Правило:** источник состояния минимален,
  производные значения вычисляются чистым `computed`; `computed` не меняет
  состояние, не вызывает API и не отправляет события. **Исключение:** нет.
  **Проверка:** ревью зависимостей и побочных эффектов.
- **Область:** `watch` и `watchEffect`. **Правило:** используйте их только для
  синхронизации с внешним состоянием или побочного эффекта; зависимости
  `watchEffect` должны быть очевидны, а асинхронный эффект, подписка, таймер и
  запрос получают cleanup через `onCleanup` или `onWatcherCleanup`.
  **Исключение:** cleanup не нужен для синхронного эффекта без ресурса.
  **Проверка:** ревью эффекта и ручная проверка быстрой смены входа.
- **Область:** размер и ответственность компонента. **Правило:** экран и shell
  координируют сценарий, дочерний компонент отвечает за одну часть UI; извлекайте
  компонент или composable при двух независимых обязанностях, трёх независимых
  UI-секциях, повторяемом блоке или повторно используемой реактивной/побочной
  логике. **Исключение:** маленький одноцелевой компонент без этих признаков.
  **Проверка:** ревью ответственности, `props` и событий.

## Контракты и атрибуты

- **Область:** публичный API компонента. **Правило:** данные идут вниз через
  типизированные `defineProps`, действия — вверх через типизированные
  `defineEmits`; входные области описываются `defineSlots`, значения по
  умолчанию — `withDefaults` и типизированной константой. `defineModel`
  используется только для реального двустороннего контракта. **Исключение:**
  область вставки не описывается, если компонент её не принимает. **Проверка:**
  `npm run typecheck` и история компонента.
- **Область:** wrapper с несколькими корнями либо особым корнем. **Правило:**
  отключите неявное наследование через `defineOptions({ inheritAttrs: false })`,
  получите атрибуты через `useAttrs` или `$attrs` и явно передайте разрешённые
  `attrs`, классы, обработчики и области корневому элементу. **Исключение:**
  одно-корневой компонент без преобразования атрибутов использует стандартное
  наследование. **Проверка:** история с `class`, `data-*`, `aria-*` и событием.

## Vuetify и переиспользуемый UI

- **Область:** продуктовый wrapper над Vuetify или HTML. **Правило:** wrapper
  имеет узкий типизированный публичный API, семантический корень, явную передачу
  разрешённых `props`, событий, slots и attrs; внешний код использует этот API,
  тему и tokens продукта. **Исключение:** прямой `v-*` допустим для layout или
  локального примитива без продуктового контракта. **Проверка:** история и
  ревью публичных `props`.
- **Область:** вызов Vuetify. **Правило:** feature не зависит от внутреннего DOM
  Vuetify, селекторов `.v-*` и неофициальных деталей компонента. **Исключение:**
  нет; нужное поведение добавляется в wrapper. **Проверка:** поиск селекторов и
  ревью стилей.
- **Область:** доступность wrapper и экрана. **Правило:** сохраняйте нативную
  семантику, доступное имя, `disabled` и применимые `aria-*`; полные требования
  взаимодействия задаёт [нота доступности](UI-accessibility.md).
  **Исключение:** для back-office действует
  [контракт новой версии](../../back-office/docs/10-architecture/ui-ownership.md).
  **Проверка:** состояния истории и браузерная проверка по стратегии проверки.

## Стили и доказательства

- **Область:** компонентные стили. **Правило:** стили остаются в SFC с
  `<style scoped>`; `lang="scss"` применяйте только когда нужны возможности Sass
  или его требует проект. Селекторы опираются на собственные классы, значения
  цвета, размеров, интервалов, радиусов, теней и состояний — на tokens.
  **Исключение:** глобальные CSS/SCSS содержат только tokens, тему, reset и
  правила приложения; CSS custom properties не требуют Sass. **Проверка:**
  ревью SFC и global styles.
- **Область:** проникновение в дочерний DOM. **Правило:** `:deep()` применяйте
  только для документированного внешнего ограничения; `!important` — только
  когда каскад и публичный API не решают конфликт. Raw values допускаются лишь
  для одноразовой геометрии или значения без product token. **Исключение:**
  причина и граница каждого такого случая фиксируются комментарием рядом.
  **Проверка:** ревью селектора и токенов.
- **Область:** повторно используемый компонент без runtime consumer.
  **Правило:** его контракт подтверждается типизированным API и проверкой
  компонента; story не является обязательным доказательством. Когда компонент
  входит в пользовательский сценарий, его runtime-состояния проверяются по
  [стратегии проверки](Validation-strategy.md). **Проверка:** ревью публичного
  API, применимые тесты и browser evidence для runtime consumer.

## Форматтер, линтер и пустые строки

Prettier и ESLint обязательны для изменённого frontend-кода, включая новый
back-office. Источник настроек форматирования — корневой
[`.prettierrc.json`](../../.prettierrc.json); версии инструментов фиксируются
в manifest и lock-файле. Локальный ESLint проверяет TypeScript/Vue и правила
читаемости, не дублируя настройки отступов и кавычек Prettier.

- Между импортами и остальным кодом, самостоятельными функциями и соседними
  блоками `template`, `script`, `style` оставляй одну пустую строку.
- Внутри функции отделяй пустой строкой проверку входов, основное действие
  и итоговый `return`, если перед ним есть другие инструкции. В SFC разделяй
  группы входных контрактов, состояния, производных значений, обработчиков
  и подписок. Внутри каждого блока инструкции остаются рядом, если выполняют
  один связный шаг; пустая строка после каждой инструкции не требуется.
- Связанные импорты и короткие объявления одной группы могут идти подряд.
  Самостоятельные многострочные объявления разделяй пустой строкой.
- Не оставляй несколько пустых строк подряд или пустую строку сразу после
  открывающей либо перед закрывающей скобкой блока. Файл заканчивается переводом
  строки. Для очень короткой функции с одним действием разделитель не нужен.

Пример разделения шагов:

```ts
function submitOrder() {
  if (!canSubmit.value) {
    return;
  }

  const payload = buildPayload();

  return orders.submit(payload);
}
```

Prettier сохраняет уже расставленные пустые строки, сокращает несколько подряд
до одной и удаляет их по краям блоков; он не добавляет разделители логических
шагов автоматически. Это поведение описано в
[официальной документации](https://prettier.io/docs/rationale#empty-lines).
Наличие нужных разделителей проверяется на ревью после форматирования.

При настройке ESLint нового back-office обязательны
[`@stylistic/padding-line-between-statements`](https://eslint.style/rules/padding-line-between-statements)
для разделителей после группы импортов и объявлений, между самостоятельными
функциями, после управляющего блока и перед `return`, и
[`@stylistic/no-multiple-empty-lines`](https://eslint.style/rules/no-multiple-empty-lines)
с `max: 1`, `maxBOF: 0`, `maxEOF: 0`. Последовательные импорты и связанные
объявления допускаются без разделителя. Семантические группы, которые линтер
не различает, проверяются по правилам выше. Это требование к новой конфигурации,
а не утверждение, что эти правила уже включены в существующих приложениях.

Для текущего изменения запускай существующие команды форматирования и lint
в пределах затронутых файлов. Отсутствие настроенного инструмента укажи
в отчёте; не объявляй проверку пройденной. Не используй `prettier-ignore`
или отключение ESLint для обхода этих правил.

## Имена, комментарии и проверка

- **Область:** имена. **Правило:** имена компонентов пользовательской области и
  файлов — `PascalCase`, переменных и функций — `camelCase`, событие называет
  действие; атомы используют соглашение владельца продукта, включая `Ui*` и
  kebab-тег там, где оно принято. **Исключение:** существующее соглашение
  продукта не меняется вне задачи. **Проверка:** ревью изменённых имён.
- **Область:** комментарии. **Правило:** комментарий объясняет нетривиальную
  причину, ограничение или обход, но не пересказывает очевидный код.
  **Исключение:** отсутствует. **Проверка:** ревью diff.
- **Область:** изменённый проект. **Правило:** отформатируйте код и запустите
  `npm run format:check`, `npm run lint`, `npm run typecheck`.
  **Исключение:** неприменимая команда указывается в
  отчёте с причиной. **Проверка:** отчёт задачи.
