# Стиль Vue-кода

Это главный источник правил Vue и Vuetify для всего UI-кода `front-office` и
`back-office`, включая runtime UI и истории. Каждый клиент сохраняет свои
соглашения об именах и компоновке; общих UI- или npm-пакетов и импортов между
клиентами нет по [[../20-architecture/Repository-boundaries|границам
приложений]]. Истории импортируют готовый runtime UI по
[[../50-interfaces/Storybook-gates|барьерам Storybook]].

## Компонент и шаблон

- SFC использует Composition API, `<script setup lang="ts">` и
  типизированные контракты; порядок блоков: `template`, `script`, `style`.
- Шаблон декларативен: повторные и составные условия, фильтрация, сортировка,
  классы и карты представления выносятся в `computed` или типизированную карту.
- `v-if` создаёт редко показываемый или дорогой блок, `v-show` сохраняет часто
  переключаемый; `v-if` и `v-for` не ставятся на один элемент, а каждый `v-for`
  имеет стабильный примитивный `:key`. Ключ-индекс допустим только для
  неизменяемого списка без локального состояния элементов.
- `switch` и карта представления покрывают каждый вариант union; недостижимый
  вариант завершается проверкой `never`. Fallback допустим только для внешнего
  нетипизированного формата с явной обработкой ошибки.

## Реактивность и границы компонентов

- Источник локального состояния минимален; производные значения — чистый
  `computed`, который не меняет состояние, не вызывает API и не отправляет
  события.
- `watch` и `watchEffect` служат синхронизации с внешним состоянием или
  побочному эффекту. Асинхронный эффект, подписка, таймер и запрос получают
  cleanup через `onCleanup` или `onWatcherCleanup`.
- Экран и shell координируют сценарий, дочерний компонент отвечает за одну
  часть UI. Компонент или composable выделяется при независимых обязанностях,
  секциях, повторяемом блоке либо повторно используемой реактивной логике.
- Данные идут вниз через типизированные `defineProps`, действия — вверх через
  типизированные `defineEmits`; slots описываются `defineSlots`, значения по
  умолчанию — `withDefaults` и типизированной константой. `defineModel`
  применяется только для реального двустороннего контракта.
- Wrapper с несколькими либо особым корнем отключает неявное наследование через
  `defineOptions({ inheritAttrs: false })`, получает атрибуты через `useAttrs`
  или `$attrs` и явно передаёт разрешённые attrs, классы, обработчики и slots
  корневому элементу. Однокорневой компонент без преобразования атрибутов
  использует стандартное наследование.

## Vuetify, стили и истории

- Продуктовый wrapper над Vuetify или HTML имеет узкий типизированный API,
  семантический корень и явную передачу разрешённых props, событий, slots и
  attrs; прямой `v-*` допустим для layout или локального примитива без
  продуктового контракта.
- UI не зависит от внутреннего DOM Vuetify, селекторов `.v-*` или
  неофициальных деталей компонента; нужное поведение добавляется в wrapper.
- Сохраняются нативная семантика, доступное имя, `disabled` и применимые
  `aria-*`; полные требования определяет [[UI-accessibility|нота доступности]].
- Компонентные стили остаются в SFC с `<style scoped>`; селекторы используют
  собственные классы, а цвета, размеры, интервалы, радиусы, тени и состояния —
  tokens продукта. `lang="scss"` применяется, когда нужны возможности Sass или
  его требует проект; глобальные CSS/SCSS содержат только tokens, тему, reset и
  правила приложения. Raw values допустимы для одноразовой геометрии или
  значения без product token. `:deep()` и `!important` требуют комментария с
  причиной и границей.
- История импортирует готовый runtime-компонент и показывает его публичные
  props, slots, события и применимые loading, empty, error и disabled состояния.

## Имена, комментарии и проверка

- Компоненты пользовательской области и файлы — `PascalCase`, переменные и
  функции — `camelCase`, событие называет действие; принятые соглашения каждого
  клиента не меняются без отдельной задачи.
- Комментарий объясняет нетривиальную причину, ограничение или обход, а не
  пересказывает код.
- Форматирование, lint, typecheck, сборка Storybook и применимые тесты
  выполняются по [[Validation-strategy|стратегии проверки]].
