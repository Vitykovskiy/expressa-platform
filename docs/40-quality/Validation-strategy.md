# Стратегия проверки

Это стратегия проверки всего Vue UI в `front-office` и `back-office`, а не
отчёт о выполненных тестах. Требования взаимодействия и доступности задаёт
[одноимённая quality-нота](UI-accessibility.md). Playwright даёт свидетельство
наблюдаемого поведения, но не определяет требования и не заменяет источник
истины.

Admin и Customer независимы: каждый владеет собственными design tokens и
runtime UI; общих UI/npm-пакетов и импортов между продуктами нет.

## Обязательные уровни

- Сборка, typecheck и lint — в каждом изолированном npm-проекте.
- Модульные тесты — для логики с самостоятельными входами и выходами.
- Playwright в реальном браузере — для ключевых пользовательских потоков и наблюдаемого вида.
- Проверки доступности и взаимодействия выполняются в границах [профильной quality-ноты](UI-accessibility.md).

## Ширины браузера

Проверяйте `479`, `480`, `767`, `768`, `1023`, `1024` px там, где экран или
компонент зависит от ширины. Для Admin критична граница `768`; для Customer —
границы `480` и `1024`.

## Браузерная UI-приёмка

После разработки и автоматических проверок разработчик проверяет в реальном
браузере реальные пользовательские сценарии. Матрица доказательств покрывает
экран × сценарий × состояние × viewport: каждый изменённый экран в `default`,
все изменённые состояния и переходы, а при изменении layout — минимальную и
максимальную ширину и обе стороны каждого затронутого breakpoint.

Разработчик сохраняет отчёт в
`.codex/tmp/tasks/<task-id>/ui-acceptance/report.md`; снимки этой же итерации
именуются `iteration-<n>-<screen>-<scenario>-<state>-<viewport>.png`. Отчёт
содержит hash `HEAD` и diff, окружение, браузер, timestamp, действия,
результаты console/page/network, документации и runtime, дефекты, повторный
запуск и итоговый вердикт. Screenshot — доказательство приёмки; автоматические
тесты не заменяют проверку runtime.

`reviewer_owner` независимо проверяет живой UI и каждый screenshot, фиксирует
вердикт и владеет циклом fix/rerun. Самоприёмка, отсутствующие или устаревшие
доказательства, любой подтверждённый UI/UX-дефект или отсутствие свежего
положительного вердикта — провал. После трёх неуспешных итераций задача получает
`blocked` либо `split_required`; waiver не допускается. `integration reviewer`
не может дать `approved` без свежего положительного вердикта.

## Выполнение

Применимые команды определены в `front-office/package.json` и
`back-office/package.json`: форматирование, lint, typecheck, unit-тесты, сборка
и e2e.
