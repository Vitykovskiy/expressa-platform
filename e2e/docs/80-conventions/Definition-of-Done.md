# Definition of Done для standalone E2E

Документ задаёт постоянный перечень критериев приёмки E2E-кода. Это не шаблон задачи: агент подтверждает в отчёте все применимые пункты, но не отмечает и не изменяет чекбоксы при выполнении задачи. Структуру кода определяет [Code Style](Code-style.md), а UI-only границу — [ADR-001](../20-architecture/ADR/ADR-001-standalone-e2e-architecture.md).

## Сценарий и границы

Нормативные правила сценария, JSDoc, `test.step` и объектов определяет
[Code Style](Code-style.md). Этот DoD проверяет их соблюдение и не задаёт второй
вариант правил.

Перед приёмкой изменённого сценария подтверждаются все пункты:

- [ ] Каждый `test` имеет JSDoc ровно с четырьмя разделами из Code Style: `Назначение`, `Предусловия`, `Сценарий`, `Ожидаемый результат`.
- [ ] `Предусловия` существуют до начала `test`, и для каждого указан источник: изолированный профиль, тестовое окружение или доступная роль.
- [ ] `Сценарий` содержит атомарные предметные действия пользователей в фактическом порядке: один пункт изменяет одно значение, выбирает одну предметную опцию, запускает создание одного объекта либо сохраняет один объект; несколько вводов, выборов или сохранение не объединены.
- [ ] Каждый пункт `Сценария` соответствует ровно одному прямому вызову публичного действия Page/Component Object в spec и находится с ним в том же порядке; один метод не скрывает несколько пунктов сценария.
- [ ] Каждая смысловая контрольная точка `Ожидаемого результата` имеет один одноимённый русскоязычный business-level `test.step` в том же порядке.
- [ ] Business-level `test.step` объединяет проверки одного предметного состояния; действия Page/Component Object не оборачиваются внешним wrapper-step, а отдельные поля одного состояния не дробятся на самостоятельные steps.
- [ ] Внутри business-level `test.step` каждое независимо проверяемое значение имеет отдельный `expect` с собственным сообщением; наименование, вариант, добавки, количество, цена, итог и статус не скрыты общим assertion-методом.
- [ ] Атомарный `test` проверяет одну capability. Ненумерованная подготовка содержит только авторизацию через UI, если она не является целью сценария; предметные UI-действия отражены в нумерованном `Сценарии`.
- [ ] Сквозной `full journey` существует отдельно от атомарных tests и проверяет их связку, а не подменяет каждую capability.
- [ ] Spec владеет последовательностью пользовательского сценария, business-level шагами и межэкранными предметными сравнениями; Page — входом на экран и композицией; Component — локаторами, UI-действиями, готовностью и непосредственными web-first проверками.
- [ ] Подготовка, действия и проверки используют только Playwright UI: без API, БД, Web Storage, прямого изменения сети и иных технических каналов.
- [ ] Fixture предоставляет только технические зависимости и не авторизует пользователя, не создаёт предметные данные и не изменяет состояние приложения.
- [ ] Сценарий независим от порядка запуска: использует неизменяемые данные профиля либо собственные уникальные данные и не рассчитывает на восстановление seed между тестами.
- [ ] Если для устойчивого UI-контракта нужен `data-testid` или иной атрибут в front-office либо back-office, изменение проходит DoD и валидации owning-контура; E2E использует этот контракт только через UI.
- [ ] Изменение не затрагивает локальные E2E-наборы приложений и инфраструктуру запуска без отдельного решения.

## Объекты и ожидания

- [ ] Spec не содержит локаторов, `getByTestId`, технических кликов, ручных ожиданий и wrapper-steps без собственной предметной проверки.
- [ ] Каждое системное UI-значение из конечного набора выражено TypeScript `enum` владельца Page/Component Object; публичный API принимает этот `enum`, а spec и тестовые данные передают его член. Строковый литерал, общий `string`, string literal union, constants-object и отдельный метод для каждого значения не заменяют `enum` и запрещены.
- [ ] Свободные пользовательские и созданные сценарием данные остаются `string`; технические ключи полей, `data-testid` и строки локаторов не выходят из private-реализации Page/Component Object.
- [ ] Page остаётся тонким корнем композиции; workflow нескольких устойчивых областей не скрыт в Page или Component Object.
- [ ] Component одной Page лежит в каталоге этой Page. В `components` находится только shared Component, который используют минимум две Page.
- [ ] `*.constants.ts` и `*.types.ts` принадлежат одному Page или Component, лежат рядом с владельцем и имеют его базовое имя; каждый именованный module-scope `const` статического UI- или config-контракта находится в `<owner>.constants.ts`, а каждый именованный module-scope `type`, `interface` или `enum` владельца — в `<owner>.types.ts`, независимо от `export` и повторного использования. Локальные переменные, параметры методов и private Locator-поля не выносятся.
- [ ] Межкаталожные импорты используют `@pages/*`, `@components/*`, `@fixtures/*` или `@support/*`; относительный импорт не выходит за каталог владельца.
- [ ] Локаторы приватны и используют допустимый устойчивый контракт; CSS-классы, HTML-теги, DOM-порядок, `.first()`, `.last()` и `nth()` не служат тестовым контрактом.
- [ ] Каждое публичное UI-действие ожидает наблюдаемый пользователю результат через web-first `expect`; фиксированные задержки и ожидания внутренних технических событий отсутствуют.
- [ ] Имена шагов и UI-ассертов написаны по-русски и называют ожидаемый эффект; структура импортов и класса соответствует Code Style.

## Код, данные и документация

- Изменение минимально: без временных обходов, отладочного кода, сфокусированных и отключённых тестов.
- `fixtures/test.ts` собирает зависимости, `support/data` содержит предметные данные, `support/config` читает и проверяет окружение. Секреты и учётные данные не фиксируются в spec или документации.
- Изменение сценария, объекта, fixture, данных, конфигурации или правил сопровождается актуализацией соответствующей ноты в `e2e/docs`.

## Проверки

Перед завершением нетривиальной задачи выполняются применимые команды из `package.json`:

```bash
npm run lint
npm run format:check
npm run typecheck:e2e
```

Полные E2E-сценарии запускаются только с предоставленными `E2E_FRONT_OFFICE_URL` и `E2E_BACK_OFFICE_URL`.

Для изменений сценариев E13 выполняется набор из
[карты E2E-сценариев](../95-testing/E2E-map.md) в подготовленной среде без
зависимости от порядка и данных предыдущего запуска. Повторная проверка того же
commit запускается оператором через `Re-run jobs` в GitHub Actions.
