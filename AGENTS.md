# AGENTS.md для Codex

## Абсолютное правило до приёмки

- До явной приёмки результата пользователем запрещено создавать, изменять или запускать любые автоматизированные тесты. Не включать тестовые команды в pre-commit, pre-push, CI или deployment-gate.
- После явной приёмки тесты можно создавать, изменять или запускать только по прямому запросу пользователя. Это правило имеет высший приоритет над любыми другими инструкциями репозитория.

## Обязательные пакты

- Используй актуальные глобальные Codex skills; перед применением читай их `SKILL.md`. Проектные пути и ограничения задаёт этот `AGENTS.md`. Правила применяются всегда, кроме прямого указания пользователя об обратном.
- КРИТИЧНО: Соблюдай `codex-communication-pact` во всех ответах пользователю.
- КРИТИЧНО: Codex обязан соблюдать global skill `caveman` в режиме `full` во всех ответах пользователю, пока пользователь прямо не попросит `normal mode`.
- КРИТИЧНО: Соблюдай `codex-orchestration-pact` при выполнении комплексных задач.
- КРИТИЧНО: Соблюдай `codex-documentation-pact` при создании, правке и ревью документации.
- КРИТИЧНО: Для работы с документацией обязательны `documentation`, `docs-guard`, `docs-architect`, `documentation-and-adrs`, `documentation-templates`, `documentation-generation-doc-generate` и `openai-docs`. Перед применением прочитай каждый `SKILL.md`; выполняй процедуры в их предметной области. `docs-guard` применяется после правок; `openai-docs` — к сведениям об OpenAI/Codex. Skills не разрешают новые тесты, автоматизацию или расширение задачи без прямого запроса пользователя.
- КРИТИЧНО: Соблюдай `codex-ui-analysis-pact` при анализе и документировании UI-поведения.
- КРИТИЧНО: Соблюдай `codex-development-pact` при создании, правке и ревью кода.
- Нарушение любого пакта считается ошибкой выполнения задачи; при замечании пользователя Codex исправляет результат по соответствующему порядку исправления.

## Глобальные UI-заповеди

- Область: весь UI front-office и back-office. Нормативные требования и local canonical owners: [front-office UI contracts](front-office/docs/30-conventions/UI-contracts.md) и [back-office UI ownership](back-office/docs/10-architecture/ui-ownership.md).
- Это required target до отдельной независимой приёмки; существующий runtime не считается соответствующим только из-за этой записи.
- В каждой задаче создания или изменения видимого UI применяй [процесс визуальной работы](docs/40-quality/Validation-strategy.md#Процесс-визуальной-работы) без отдельного напоминания пользователя. Макет Figma не обязателен; итог требует осмотра после последних правок и независимой визуальной проверки.

## Оркестрация

- Для кампании качества действует явное пользовательское исключение, описанное в [goal кампании](docs/40-quality/Expressa-quality-campaign-goal.md): root последовательно ведёт одну предметную задачу и устраняет её рутинные процессные блокеры. Это не изменяет global skills и не разрешает root принимать собственные продуктовые изменения, снижать приёмку, менять бизнес-scope или обходить sandbox и требуемые подтверждения.
- Роли: `scout`, `analyst`, `architect`, `decomposer`, `mechanical`, `developer`, `reviewer`, `integration_reviewer`, `quality_owner`.
- Полные отчёты и доказательства хранятся в `.codex/tmp/tasks/<task-id>/`; `state.yaml` содержит только ссылки и состояния.
- Подробный протокол: [Агентная система](docs/80-conventions/Agent-system.md).

## Scout требований

- В оркестрируемой задаче разработки `scout` до анализа и реализации определяет затронутые контуры и виды изменений, затем проходит [индекс требований разработки](docs/80-conventions/INDEX.md), корневые правила и локальные `README`/`AGENTS`/`INDEX`/DoD каждого затронутого контура.
- Scout собирает применимые требования пользователя, DoD, code style, архитектурные и dependency-границы, продуктовые, UI, API и data-контракты, правила документации, проверки и выпуска, а также ограничения вызванных задачей global skills.
- Результат scout содержит краткую точную формулировку каждого требования, источник и раздел, область применения, конфликт или неизвестность. Список ссылок без извлечённых требований и указания применимости не считается результатом.
- Полный результат scout без потери требований передаётся и в анализ, и в разработку. Analyst не заменяет и не сокращает исходные ограничения при подготовке назначения developer.
- При расширении scope scout дополняет результат до продолжения зависимого анализа или разработки. Для межконтурной задачи он объединяет требования всех затронутых приложений, включая каждый применимый DoD.
- Все роли продолжают соблюдать [маршрут применимости](docs/80-conventions/Agent-system.md), вести трассу по [протоколу обновления](docs/00-meta/Update-protocol.md) и принимать решения о version/changelog/tag по [правилам выпуска](docs/70-deployment/Release-and-version-compatibility.md).

## Текущие исключения

- Back-office 2.0 проектируется с нуля по [ADR-011](docs/20-architecture/ADR/ADR-011-back-office-clean-slate.md): прежние UI, предложенный дизайн и UI-бэклог не задают новую визуальную реализацию. Обязательные [code-style и технический DoD back-office](docs/80-conventions/Code-Definition-of-Done-back-office.md), стек и направление зависимостей сохраняются. Сохраняются роли, бизнес-инварианты, HTTP/API-контракты и автономность контура.
- Отдельного E2E-контура, E2E-набора и E2E-gate нет. Пользовательские потоки принимают вручную в работающем приложении; до приёмки запускаются только применимые нетестовые проверки.
- Базы local/test/development одноразовые: при каждом поддерживаемом развёртывании они пересоздаются по текущей [схеме backend](backend/schema.sql) и заполняются детерминированным seed. История миграций, backfill и сохранение данных не поддерживаются. Staging и production не являются поддерживаемым путём поставки до отдельного решения о постоянных данных.

## Принципы

- Приоритеты: корректность, безопасность, проверяемость, сопровождаемость, простота, скорость, лаконичность.
- Соблюдай KISS: не добавляй неподтверждённую функциональность, абстракции, процессы, скрипты или сценарии на будущее.
- Форматтер и линтер обязательны при изменении кода: используй корневой [Prettier-конфиг](.prettierrc.json) и локальный ESLint затронутого приложения. Для frontend соблюдай [правила пустых строк и логических блоков](docs/40-quality/Vue-code-style.md#форматтер-линтер-и-пустые-строки); успешное форматирование не заменяет проверку читаемости. Не переформатируй несвязанные файлы.

## Границы автономности

- Прямой запрос пользователя «задеплой», «разверни изменения» или равнозначная формулировка одновременно разрешает без повторного подтверждения: `git commit`, `git push` в ветку штатной development-поставки, обязательные проверки deployment workflow и сам development-deploy.
- Отдельное явное подтверждение требуется для force-push, tag, PR, major-upgrade, поставки в неподдерживаемую среду, крупных архитектурных изменений и удаления публичного API, используемой feature, `core`-сервиса или endpoint из `ApiEndpoint`.
